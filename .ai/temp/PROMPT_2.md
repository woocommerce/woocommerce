### Technical Clarifications

> PHP 8.5 doesn't exist yet

Yes it does, it was released on November 2025: https://www.php.net/releases/8.5/en.php

> Endpoint descriptor format - The markdown table format is unusual. Would YAML frontmatter be more maintainable?

I know it's unusual, but it's a deliberate design decision because I want most of the file (anything after the header) to be plain markdown. Using yaml (or any other structures format) might require escaping the markdown and could lead to parsing errors. Since the endpoint descriptors will mostly be automatically generated by the tool anyway (in the form of templates with placeholders) and there will be validation for these, it should be fine.

> WordPress schema often has different argument schemas for GET vs POST on the same route. Should descriptors be per-verb, or one descriptor covering all verbs with the tool merging schemas?

When there are differences in input/output for each verb, use one descriptor per verb. Collapse verbs in a single descriptor *only* when the semantics and inputs/outputs are identical for all the involved verbs.

> How should the tool match descriptors to schema endpoints? Exact regex match? The route patterns contain regex like `(?P<product_id>[\d]+)` - how will these be normalized?

Schema matching for the purposes of locating the proper endpoint descriptor will be done using exact matches, as in the provided example (`| route    | /wc/v3/products/(?P<product_id>[\\d]+)/variations/(?P<id>[\\d]+)`). For the documentation, however, this should be in a more human-readable form, e.g. `/wc/v3/products/{product_id}/variations/{id}` or `/wc/v3/products/PRODUCT_ID/variations/ID`.

### Filtering & Scope

> `/wp-json` returns ALL routes (core WordPress, other plugins). Should the tool filter only `/wc/v*` routes, or is there a configuration for which route prefixes to include?

Yes, take only whe `/wc/*` routes.

> Some endpoints may only appear when authenticated. How should the tool authenticate when fetching the schema?

Are you sure of this? `wp-rest-api-schema.json` lists endpoints that require authentication, like the ones for products or orders.

That said, if really necessary, the tool can accept an optional authentication token to be used to make the request.

## Potential Improvements

> WordPress schema doesn't always include response schemas for all endpoints. The tool may need to handle missing response definitions gracefully.

We can add a new capability to the tool: analyze the WordPress schema and flag any incomplete parts.

Additionally, the "generate site" command can have an option to exclude incomplete endpoints.

> How will authentication be shown? Should there be example request/response bodies with sample data?

The curl example can just include the required authentication header for endpoints that require it. If that information (whether authentication is required or not) can't be inferred from the schema, a new `auth` line can be added to the header in the endpoint descriptor.

> For large APIs, regenerating everything is slow. Consider tracking changes and only regenerating affected pages.

Good point but for the first iteration we'll just generate everything every time.

> Add a command to validate all descriptor files for syntax/completeness before generation.

Good idea, let's do that.

> Consider linking endpoints to their PHP source files in the WooCommerce repo for developers who want to dig deeper.

Good point but there's no way to infer which source file does an endpoint belong to, so the information would have to be manually introduced in the endpoint descriptors, right?

## Missing Details

> What hashing algorithm for the ETag?

MD5 is good enough.

> How deep can category hierarchy go? (`v3/Products/Variations/Attributes`?)

Let's say four levels as in your example.

> Error handling strategy (malformed descriptors, unreachable server, etc.)

Simple approach: show an error to the user and finish the execution returning an error code. When possible, continue execution and show all the errors at the end (e.g. malformed descriptors).

> Will old API versions (v1, v2) be included or just current?

All `wc/*` endpoints served by WooCommerce core (and included in the schema returned by WordPress) will be included. Which means that a requirement is that the served queried for the schema must NOT have any active plugin that adds enpoints in the `wc/` namespace.
