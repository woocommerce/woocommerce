## Summary of What I Understood

The project aims to build a **GraphQL-only API** for WooCommerce with these layers:

1. **Code API** (authoritative, manually maintained): PHP classes using the command pattern, with DTO classes for input/output types, and PHP 8.1 enums.
2. **GraphQL infrastructure** (auto-generated): A build script using reflection on the code API classes generates all the `webonyx/graphql-php` schema types, resolvers, and wiring.
3. **Build script** (design-time only, not shipped): Scans `src/Api/` classes, reads PHP 8 attributes + type hints, and generates everything in an `Autogenerated/` directory.

### Key design elements from the prior art (adapted for PHP 8.1+ / GraphQL-only):

- **API classes** live in `src/Api/`, with sub-directories `Enums/`, `InputTypes/`, `ObjectTypes/`, `Interfaces/`
- **Enums** can now be native PHP 8.1 `enum` types (no more class-constants workaround)
- **Interfaces** are modeled as PHP traits (for property reuse across DTOs)
- **Attributes**: `WebQuery`, `WebMutation`, `Description`, `ArgDescription`, `EnumType`, `ArrayType`, etc.
- **`$_fields_info`** optional parameter on API methods for selective field loading
- **Error handling**: client-aware exceptions surface messages; others return generic errors
- **Auth**: integrate WordPress roles/capabilities (was left out of prior PoCs)

## Questions and Clarifications

1. **Directory location**: The prior art placed the code API in `src/Api/` (public, backwards-compatible). Do we keep this, or since this is a hack week project, should it live in `src/Internal/` instead? This has implications for namespace (`Automattic\WooCommerce\Api` vs `Automattic\WooCommerce\Internal\Api`).

2. **Enums as native PHP enums**: Since we're PHP 8.1+, should enums be `enum Foo: string` (backed enums) so they serialize naturally to GraphQL enum values? This would eliminate the need for `EnumType` attributes on properties — the type system alone would suffice. Do you agree, or do you still want `EnumType` attributes for cases where the PHP type hint is `string`/`int` but logically constrained to an enum?

3. **Interfaces as traits**: The prior art used traits because PHP interfaces can't have properties. In PHP 8.1+ this is still the case. However, traits prevent actual type-checking (`$x instanceof SomeInterface` doesn't work with traits). Would you want a dual approach (a real PHP interface for type-checking + a trait for the properties), or are traits alone sufficient for this project?

4. **Field arguments**: Document 4 explicitly listed "field arguments" as a missing piece. Should we include a mechanism for field-level arguments (e.g., `total_amount(decimals: 4)`) in the spec, or defer this?

5. **Cursor-based pagination**: Document 3 sketched cursor connections. Should we spec this as the pagination mechanism, or is simple offset/limit sufficient for now?

6. **Auth integration**: You mentioned reusing WordPress roles/capabilities. Should this be:
   - Per-query/mutation via attributes (e.g., `#[RequiredCapability('manage_woocommerce')]`)?
   - Per-API-class (inherited by all its methods)?
   - Both (class-level default, method-level override)?

7. **`$_fields_info` naming**: In a GraphQL-only world, the `$_fields_info` parameter is the `ResolveInfo` object from `webonyx/graphql-php` (or a simplified version of it). Should we pass the actual `GraphQL\Type\Definition\ResolveInfo` to API methods, or a simplified array as in the prior art? The former is more powerful but couples the code API to the GraphQL library.

8. **Build script output**: The prior art generated REST controllers + GraphQL types + service providers. For GraphQL-only, the output would be:
   - GraphQL type definitions (ObjectType, InputObjectType, EnumType, InterfaceType)
   - Root Query and Mutation type with field resolvers
   - A service provider for DI registration
   - Is there anything else you'd want generated (e.g., documentation markdown)?

## Suggestions

1. **Use PHP 8.1 backed enums everywhere** and drop `EnumType` attributes. The build script can detect `enum` types via reflection. This simplifies the developer experience significantly.

2. **Consider using PHP 8 constructor promotion** in DTO classes for input types, making them immutable. Output types can remain plain public-property DTOs.

3. **For the build script**, consider generating a single `schema.php` file that returns the complete `GraphQL\Type\Schema` object, rather than individual type files. This would be simpler and aligns with how `webonyx/graphql-php` is typically used. Alternatively, a lazy-loading approach (one file per type) would be better for performance with large schemas.

4. **Error handling**: Consider defining a `GraphQLException` class with HTTP status code and optional `extensions` array (per the GraphQL spec's error extensions mechanism), rather than the `rest_response` property approach from the REST-era prior art.

5. **For auth**, a `#[RequiredCapability('capability_name')]` attribute seems cleanest, applicable to both API classes and individual methods, with method-level overriding class-level.
