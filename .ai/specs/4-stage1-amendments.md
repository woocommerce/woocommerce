Highlights:

- `src/Api` is the public, GrahphQL-unaware code API. We are still using GraphQL terminology here (queries, mutations, scalars...) because these concepts are by themselves useful for a code API.
- `src/Internal/Api` contains all the GraphQL-specific infrastructure code. 
  - The `Autogenerated` directory is where all the code from the build-time script will be placed.
  - Everything else in `Api/` is manually maintained infrastructure code.

## 3. Naming conventions

Let's keep the original PascalCase (don't convert to camelCase) for query and mutation classes. Otherwise the convention suggested in this section looks good, including the optional usage of the `Name` attribute (but extending it to any entity that gets a name in GraphQL, not only classes).

## 4. Queries

- _"Each class has exactly one public method named execute"_ - classes are allowed to have more public (and protected) methods for pure code API purposes, these will be ignored by the GraphQL infrastructure.
- _"Each parameter [of `execute`] must be typed with..."_
  - Question: Does GraphQL allow mixing primitive types and input types in the list of arguments for a query? If so, good; if not, we'll need to place an additional restriction. 
  - `ArrayOf(type)` attribute: worth explicitly mentioning that the type argument must itself be one of the allowed types (recursively, so arrays can contain arrays and the like). Question: How would that work for primitive types?
- `$requested_fields` argument: let's rename it to `$_requested_fields` to 1. Make it extra clear that it's an infrastructure parameter (even if just code API infrastructure) and 2. Allow the usage of the `requested_fields` name for an actual parameter.

## 6. and 7. Types

Same consideration regarding the `ArrayOf` attribute as for queries.

## 10. Field Arguments

The suggested approach (methods instead of proerties for fields that accept arguments) has the problem that output types are not DTOs anymore. Only the query/mutation class should be concerned with field arguments, and only when `execute` is invoked.

The `2023-12-07 - HACK week recap_ one API to query them all – Proton.mhtml` document actually suggests a way to implement this ("Fields and arguments" section) via a new `$_field_arguments` parameter for the `execute` method.

For example, for this query:

```
query {
    order(id: 1234) {
        id
        total_amount(decimals: 4)
        date_created
        applied_coupons(page: 2) {
            total_amount(decimals: 4)
            type
        }
    }
}
```

...this is what `$_field_arguments` would hold:

```
[
  'total_amount' => [
    'decimals' => 4
  ],
  'applied_coupons' => [
    'page' => 2,
    '_item' => [
      'total_amount' => [
        'decimals' => 4
      ]
    ]
  ]
]
```

This implies that we need to tag each parameter accepting property with a dedicated `Parameter` that conveys name, type (including if it's nullable or not, and if it's an array or not) and then a matching `ParameterDescription` attribute. Example (might need asjustments):

```php
#[Parameter('decimals', 'int')]
#[ParameterDescription('decimals', 'Number of decimals for the value')]
public float $total_amount;
```

Question: How could nullables and arrays (plus the type of array itmes) be specified?

## 13. Authentication & Authorization

The `RequiredCapability` attribute looks good, but there should be an inheritance mechanism for it: if a query/mutation class doesn't have one, it should inherit the one in one of its parent class, implemented PHP interface, or implemented trait. If no attribute can be found upwards the inheritance/implementation chain, that's an error. If multiple attributes are found (e.g. one in the parent class and one in a trait), then all of the capabilities are required, as if they were listed in a single attribute.

Also multiple `RequiredCapability` attributes can be applied to the same class, and they are equivalent to all the capabilities specified in the same attribute.

## 14. Error Handling

The error class looks good, but let's rename `$http_status` to `$status_code` to make it "network-agnostic" (since we are defining it as part of a pure code API).

### Debug mode

The proposed `WP_DEBUG` based mechanism is fine. But if the user is an administrator, adding `_debug=1` to the query string should also trigger a fully detailed error response to be returned.

## 15. Dependency Injection

Note that WooCommerce already has a dependency injection container, `RuntimeContainer` (which gets replaced with `TestingContainer` when unit tests run), reachable via the `wc_get_container()` function, which uses injection via `init` method to specify the dependencies. This is a very simple container that just resolves existing classes by full name as singletons, no manual registration or service providers are needed.

## 16. Attributes Reference

We would need an extra attribute: `Ignore`. When applied to a query/mutation class, a DTO class or a DTO class property, then as far as the GraphQL API is concerned it's as if this class/member didn't exist (it's not exposed). Of course, a non-ignored public query/mutation/DTO class referencing an ignored class/member results in an error at build time.
