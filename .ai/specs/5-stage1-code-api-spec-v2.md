# WooCommerce GraphQL API - Code API Specification (Stage 1, v2)

## 1. Overview

The Code API is the **authoritative, manually maintained** layer from which the GraphQL API infrastructure is automatically generated. It follows the **command pattern**: each query or mutation is represented by a dedicated PHP class with a single `execute` method.

Key principles:

- **Code-first**: developers write PHP classes; the build script generates GraphQL infrastructure.
- **Convention over configuration**: directory placement and naming conventions determine behavior by default.
- **Attributes where conventions fall short**: PHP 8 attributes provide metadata that can't be inferred from the code structure itself.
- **GraphQL-agnostic**: the code API classes have zero knowledge of GraphQL. They are usable as a standalone code API even without the GraphQL infrastructure being present.

---

## 2. Directory Structure

### Public Code API (`src/Api/`)

The public, GraphQL-agnostic code API. We use GraphQL terminology (queries, mutations, scalars...) because these concepts are by themselves useful for a code API.

```
src/Api/
├── Queries/              # Query command classes (one class = one GraphQL query)
├── Mutations/            # Mutation command classes (one class = one GraphQL mutation)
├── Types/                # Output DTO classes (GraphQL object types)
├── InputTypes/           # Input DTO classes (GraphQL input types)
├── Enums/                # PHP 8.1 backed enum classes (GraphQL enum types)
├── Interfaces/           # Traits defining reusable field sets (GraphQL interfaces)
├── Scalars/              # Custom scalar type definitions (e.g. DateTime)
├── Pagination/           # Built-in cursor connection types (Connection, Edge, PageInfo)
├── Attributes/           # PHP 8 attribute class definitions (used by the build script)
└── ApiException.php      # Exception class for API errors
```

Namespace root: `Automattic\WooCommerce\Api`

### Internal GraphQL Infrastructure (`src/Internal/Api/`)

All GraphQL-specific infrastructure code. This is NOT part of the public API.

```
src/Internal/Api/
├── Autogenerated/                # All build-script output goes here
│   ├── GraphQLQueries/           # Generated resolver classes, one per query
│   ├── GraphQLMutations/         # Generated resolver classes, one per mutation
│   ├── GraphQLTypes/             # Generated type classes (object, input, enum, interface, scalar)
│   ├── RootQueryType.php         # Root Query type aggregating all queries
│   ├── RootMutationType.php      # Root Mutation type aggregating all mutations
│   └── api_generation_date.txt   # Build timestamp for staleness checking
├── Scripts/                      # Build scripts (ApiBuilder.php, etc.)
├── Templates/                    # Templates for code generation
├── GraphQLController.php         # Registers and handles the GraphQL endpoint
└── Main.php                      # Initialization entry point
```

Namespace: `Automattic\WooCommerce\Internal\Api`

**Important**: The `Autogenerated/` directory is fully regenerated by the build script; never edit files in it manually. Everything else in `src/Internal/Api/` is manually maintained infrastructure code. The `Scripts/` and `Templates/` directories are excluded from the WooCommerce build package (they are design-time only).

### Subdirectory nesting

Within each `src/Api/` sub-directory, deeper nesting is allowed for organizational purposes. For example, `src/Api/Queries/Orders/GetOrder.php` is a valid query class in namespace `Automattic\WooCommerce\Api\Queries\Orders`. The nesting does NOT affect the GraphQL name (which is always derived from the class name alone).

## 3. Naming Conventions

### GraphQL names from class names

The default GraphQL name for any entity is its PHP class name **kept as-is** (PascalCase):

| PHP class name | Entity type | GraphQL name | Rule |
|---|---|---|---|
| `GetOrder` | Query | `GetOrder` | PascalCase, kept as-is |
| `ListOrders` | Query | `ListOrders` | PascalCase, kept as-is |
| `CreateOrder` | Mutation | `CreateOrder` | PascalCase, kept as-is |
| `Order` | Object type | `Order` | PascalCase, kept as-is |
| `CreateOrderInput` | Input type | `CreateOrderInput` | PascalCase, kept as-is |
| `OrderStatus` | Enum type | `OrderStatus` | PascalCase, kept as-is |
| `HasId` | Interface | `HasId` | PascalCase, kept as-is |

The `#[Name('custom_name')]` attribute can override the default GraphQL name for **any entity**: classes, properties, methods, method parameters, and enum cases.

### Property and method names

PHP property/method names are used as-is in GraphQL:

| PHP | GraphQL |
|---|---|
| `$total_amount` | `total_amount` |
| `$date_created` | `date_created` |

The `#[Name]` attribute can override individual property/method names.

### Enum case names

Enum case names are converted from PascalCase to SCREAMING_SNAKE_CASE by default:

| PHP case | GraphQL enum value |
|---|---|
| `Pending` | `PENDING` |
| `OnHold` | `ON_HOLD` |
| `ApiV3` | `API_V3` |

The `#[Name]` attribute can override individual case names.

## 4. Queries

A query is a command class in `src/Api/Queries/` with a public `execute` method that **does not modify server state**.

```php
namespace Automattic\WooCommerce\Api\Queries;

use Automattic\WooCommerce\Api\Attributes\Description;
use Automattic\WooCommerce\Api\Attributes\RequiredCapability;
use Automattic\WooCommerce\Api\Types\Order;

#[Description('Retrieve a single order by its ID.')]
#[RequiredCapability('read_shop_orders')]
class GetOrder {
    public function execute(
        #[Description('The ID of the order to retrieve.')]
        int $id
    ): ?Order {
        // Implementation: load and return the order, or null if not found.
    }
}
```

### Rules

1. **One class = one query.** Each class has exactly one public method named `execute`; this is the method that defines the GraphQL query.
2. **Additional public methods** are allowed for code API convenience (e.g., helper accessors). These are **ignored by the GraphQL infrastructure** — only `execute` is processed.
3. **Class placement** in `src/Api/Queries/` is what makes it a query (convention). No attribute is needed to mark it as a query.
4. **`execute` method parameters** become the GraphQL query arguments. Each parameter must be typed with:
   - A primitive type: `int`, `float`, `string`, `bool`
   - An enum type from `src/Api/Enums/`
   - An input type from `src/Api/InputTypes/`
   - `array` with an `#[ArrayOf]` attribute (see section 4.1)
   - Any of the above as nullable (`?Type`)
   - Any combination of the above is valid (GraphQL allows mixing primitives and input types in argument lists).
   - Parameters with default values become optional GraphQL arguments.
5. **`execute` return type** must be:
   - An output type from `src/Api/Types/`
   - An interface type from `src/Api/Interfaces/`
   - A `Connection` (for paginated results, see section 11)
   - Any of the above as nullable (`?Type`)
   - `array` with an `#[ArrayOf]` attribute (for non-paginated lists)
6. **Dependencies** are injected via the `init` method (resolved by WooCommerce's DI container). See section 15.

### 4.1. The `ArrayOf` attribute

When a parameter, return type, or property is typed as `array`, the `#[ArrayOf]` attribute specifies the element type:

```php
// Array of a class type
#[ArrayOf(Order::class)]
public array $orders;

// Array of a primitive type (use string literal)
#[ArrayOf('int')]
public array $ids;

// Array of strings
#[ArrayOf('string')]
public array $tags;
```

Valid type arguments for `#[ArrayOf]`:
- Class references: `SomeClass::class` (for output types, input types, enums, interfaces)
- String literals for primitives: `'int'`, `'float'`, `'string'`, `'bool'`
- The type argument must itself be one of the allowed types for the context (recursively).

### Optional: requested fields hint

The `execute` method MAY accept an optional parameter `?array $_requested_fields = null`. When provided, it contains the list of fields the caller has requested, as a nested associative array (keys = field names, values = `null` for scalar fields or nested arrays for object fields). When `null`, all fields should be returned.

This parameter is **not** a GraphQL concept — it is a code API optimization hint. The build script detects it (by the exact name `$_requested_fields`) and, in the generated GraphQL resolver, passes the field selection from the incoming query. The underscore prefix signals that this is an infrastructure parameter, and it reserves the name `requested_fields` for potential use as a regular API argument.

```php
public function execute(
    int $id,
    ?array $_requested_fields = null
): ?Order {
    $order = new Order();
    $order->id = $wc_order->get_id();
    $order->status = OrderStatus::from($wc_order->get_status());

    // Only load expensive data if requested
    if ($_requested_fields === null || isset($_requested_fields['line_items'])) {
        $order->line_items = $this->load_line_items($wc_order);
    }

    return $order;
}
```

### Optional: field arguments

The `execute` method MAY accept an optional parameter `?array $_field_arguments = null`. When provided, it contains the arguments that have been supplied for individual fields in the query response. See section 10 for the full specification of field arguments.

## 5. Mutations

A mutation is a command class in `src/Api/Mutations/` with a public `execute` method that **modifies server state**.

```php
namespace Automattic\WooCommerce\Api\Mutations;

use Automattic\WooCommerce\Api\Attributes\Description;
use Automattic\WooCommerce\Api\Attributes\RequiredCapability;
use Automattic\WooCommerce\Api\InputTypes\CreateOrderInput;
use Automattic\WooCommerce\Api\Types\Order;

#[Description('Create a new order.')]
#[RequiredCapability('publish_shop_orders')]
class CreateOrder {
    public function execute(
        #[Description('Data for the new order.')]
        CreateOrderInput $input
    ): Order {
        // Implementation: create the order and return it.
    }
}
```

### Rules

All rules from section 4 (Queries) apply, with the only difference being:
- Class placement in `src/Api/Mutations/` makes it a mutation.
- Mutations typically accept a single input type argument (following GraphQL best practice), but multiple arguments (including primitives) are allowed.

## 6. Output Types (Object Types)

Output types are **pure DTO classes** in `src/Api/Types/` that represent the data returned by queries and mutations.

```php
namespace Automattic\WooCommerce\Api\Types;

use Automattic\WooCommerce\Api\Attributes\ArrayOf;
use Automattic\WooCommerce\Api\Attributes\Description;
use Automattic\WooCommerce\Api\Attributes\Parameter;
use Automattic\WooCommerce\Api\Attributes\ScalarType;
use Automattic\WooCommerce\Api\Enums\OrderStatus;
use Automattic\WooCommerce\Api\Interfaces\HasId;
use Automattic\WooCommerce\Api\Scalars\DateTime;

#[Description('Represents a WooCommerce order.')]
class Order {
    use HasId;

    #[Description('The total amount of the order.')]
    #[Parameter(name: 'decimals', type: 'int', default: 2, description: 'Number of decimal places.')]
    public float $total_amount;

    #[Description('The date the order was created, in ISO 8601 format.')]
    #[ScalarType(DateTime::class)]
    public string $date_created;

    #[Description('The current status of the order.')]
    public OrderStatus $status;

    #[Description('The customer who placed the order.')]
    public ?Customer $customer;

    #[Description('Coupons applied to this order.')]
    #[ArrayOf(AppliedCoupon::class)]
    #[Parameter(name: 'page', type: 'int', default: 1, description: 'Page number.')]
    #[Parameter(name: 'per_page', type: 'int', default: 10, description: 'Results per page.')]
    public array $applied_coupons;
}
```

### Rules

1. Output types are **pure DTOs**: public properties only, no business logic, no methods beyond what PHP requires.
2. **Properties** must be typed with:
   - A primitive type: `int`, `float`, `string`, `bool`
   - Another output type from `src/Api/Types/`
   - An enum from `src/Api/Enums/`
   - An interface from `src/Api/Interfaces/` (via `use` trait)
   - `array` with `#[ArrayOf]` (see section 4.1 for type argument rules)
   - A `Connection` type (for paginated sub-collections)
   - Any of the above as nullable
3. **`use` clauses** (traits from `src/Api/Interfaces/`) add shared fields AND declare that the GraphQL type implements the corresponding GraphQL interface.
4. **`#[Description]`** is recommended on the class and on each property.
5. Properties that accept **field arguments** are decorated with `#[Parameter]` attributes (see section 10).

## 7. Input Types

Input types are **pure DTO classes** in `src/Api/InputTypes/` used as arguments for mutations (and occasionally queries).

```php
namespace Automattic\WooCommerce\Api\InputTypes;

use Automattic\WooCommerce\Api\Attributes\ArrayOf;
use Automattic\WooCommerce\Api\Attributes\Description;
use Automattic\WooCommerce\Api\Enums\OrderStatus;

#[Description('Data required to create a new order.')]
class CreateOrderInput {
    #[Description('The initial status of the order.')]
    public OrderStatus $status;

    #[Description('The customer ID.')]
    public int $customer_id;

    #[Description('Billing address.')]
    public AddressInput $billing;

    #[Description('Tags for the order.')]
    #[ArrayOf('string')]
    public array $tags;
}
```

### Rules

1. Input types are **pure DTOs**: public properties only, no methods, no constructor logic.
2. **Properties** must be typed with:
   - A primitive type: `int`, `float`, `string`, `bool`
   - Another input type from `src/Api/InputTypes/`
   - An enum from `src/Api/Enums/`
   - `array` with `#[ArrayOf]` (see section 4.1 for type argument rules)
   - Any of the above as nullable (nullable = optional in GraphQL)
3. Properties with a default value become optional GraphQL input fields.
4. Interfaces (traits) can be used for shared field sets, but note that GraphQL input types cannot implement interfaces — the trait is purely for PHP code reuse.

## 8. Enums

Enums are PHP 8.1 backed enum classes in `src/Api/Enums/`.

```php
namespace Automattic\WooCommerce\Api\Enums;

use Automattic\WooCommerce\Api\Attributes\Description;

#[Description('The status of an order.')]
enum OrderStatus: string {
    #[Description('Order is pending payment.')]
    case Pending = 'pending';

    #[Description('Order is being processed.')]
    case Processing = 'processing';

    #[Description('Order is on hold.')]
    case OnHold = 'on-hold';

    #[Description('Order has been completed.')]
    case Completed = 'completed';

    #[Description('Order has been cancelled.')]
    case Cancelled = 'cancelled';

    #[Description('Order has been refunded.')]
    case Refunded = 'refunded';

    #[Description('Order payment has failed.')]
    case Failed = 'failed';
}
```

### Rules

1. Enums **must** be backed enums (`enum Foo: string` or `enum Foo: int`).
2. The backed value is the serialization value in GraphQL.
3. The case name (PascalCase) becomes the GraphQL enum value name, converted to SCREAMING_SNAKE_CASE by the build script by default: `Pending` → `PENDING`, `OnHold` → `ON_HOLD`.
4. The `#[Name]` attribute can override the default GraphQL name for individual cases.
5. `#[Description]` is recommended on the enum class and each case.
6. No special attribute is needed on properties that reference enums — the PHP type hint is sufficient for the build script to detect them.

---

## 9. Interfaces (Traits)

Interfaces are PHP traits in `src/Api/Interfaces/` that define reusable sets of fields.

```php
namespace Automattic\WooCommerce\Api\Interfaces;

use Automattic\WooCommerce\Api\Attributes\Description;

#[Description('An entity with a unique identifier.')]
trait HasId {
    #[Description('The unique identifier.')]
    public int $id;
}
```

### Rules

1. Interfaces are **PHP traits** (because PHP interfaces cannot declare properties).
2. When an output type `use`s a trait from `src/Api/Interfaces/`, the corresponding GraphQL object type is declared as implementing the GraphQL interface.
3. Interface traits follow the same property rules as output types (section 6).
4. Trait properties can have `#[Description]` and `#[Parameter]` attributes.
5. Traits can `use` other traits (interface inheritance).
6. When an input type `use`s a trait, it gains the PHP properties but there is no GraphQL interface relationship (GraphQL input types don't support interfaces).

## 10. Field Arguments

Some output type fields accept arguments in GraphQL (e.g., `total_amount(decimals: 4)`). Since output types must remain **pure DTOs**, field arguments are handled by the **command class** via a `$_field_arguments` parameter, with the available arguments **declared on the DTO properties** via `#[Parameter]` attributes.

### Declaring field arguments on DTO properties

Use the `#[Parameter]` attribute on output type properties to declare which arguments the field accepts:

```php
class Order {
    public int $id;

    #[Description('The total amount of the order.')]
    #[Parameter(name: 'decimals', type: 'int', default: 2, description: 'Number of decimal places.')]
    public float $total_amount;

    #[Description('Coupons applied to this order.')]
    #[ArrayOf(AppliedCoupon::class)]
    #[Parameter(name: 'page', type: 'int', default: 1, description: 'Page number.')]
    #[Parameter(name: 'per_page', type: 'int', default: 10, description: 'Items per page.')]
    public array $applied_coupons;
}
```

Multiple `#[Parameter]` attributes can be applied to a single property (one per argument).

### `#[Parameter]` attribute specification

```php
#[Parameter(
    name: string,             // Required. Name of the field argument.
    type: string,             // Required. The argument type (see below).
    nullable: bool = false,   // Whether the argument is nullable.
    array: bool = false,      // Whether the argument is a list/array.
    default: mixed = <none>,  // Default value (makes the argument optional).
    description: string = '', // Description for the GraphQL schema.
)]
```

The `type` parameter accepts:
- Primitive type strings: `'int'`, `'float'`, `'string'`, `'bool'`
- Enum/input type class references: `OrderStatus::class`, `SomeInput::class`

Examples:
```php
// Required int
#[Parameter(name: 'limit', type: 'int')]

// Nullable int
#[Parameter(name: 'limit', type: 'int', nullable: true)]

// Int with default (optional)
#[Parameter(name: 'limit', type: 'int', default: 10)]

// Array of ints
#[Parameter(name: 'ids', type: 'int', array: true)]

// Nullable array of enum values
#[Parameter(name: 'statuses', type: OrderStatus::class, array: true, nullable: true)]
```

### Alternative: `#[ParameterDescription]` attribute

For cases where the description is too long to fit in the `#[Parameter]` attribute, a separate `#[ParameterDescription]` attribute can be used instead of the `description` argument:

```php
#[Parameter(name: 'decimals', type: 'int', default: 2)]
#[ParameterDescription('decimals', 'The number of decimal places to round to. Defaults to 2.')]
public float $total_amount;
```

**Using both** the `description` argument in `#[Parameter]` AND a `#[ParameterDescription]` attribute for the same parameter is a **build error**.

### The `$_field_arguments` parameter

The command's `execute` method receives field arguments via an optional `?array $_field_arguments = null` parameter:

```php
#[RequiredCapability('read_shop_orders')]
class GetOrder {
    public function execute(
        int $id,
        ?array $_field_arguments = null
    ): ?Order {
        $order = new Order();
        $order->id = $wc_order->get_id();

        // Apply field arguments
        $decimals = $_field_arguments['total_amount']['decimals'] ?? 2;
        $order->total_amount = round((float) $wc_order->get_total(), $decimals);

        // Handle nested field arguments for sub-collections
        $coupon_page = $_field_arguments['applied_coupons']['page'] ?? 1;
        $coupon_per_page = $_field_arguments['applied_coupons']['per_page'] ?? 10;
        $all_coupons = $this->load_coupons($wc_order);
        $order->applied_coupons = array_slice($all_coupons, ($coupon_page - 1) * $coupon_per_page, $coupon_per_page);

        return $order;
    }
}
```

### Structure of `$_field_arguments`

The array is keyed by field name. Each entry contains the arguments for that field. For fields that are arrays of objects with their own field arguments, a special `_item` key contains the sub-field arguments.

For this GraphQL query:
```graphql
query {
    GetOrder(id: 1234) {
        id
        total_amount(decimals: 4)
        applied_coupons(page: 2) {
            total_amount(decimals: 4)
            type
        }
    }
}
```

The `$_field_arguments` array would be:
```php
[
    'total_amount' => [
        'decimals' => 4,
    ],
    'applied_coupons' => [
        'page' => 2,
        '_item' => [
            'total_amount' => [
                'decimals' => 4,
            ],
        ],
    ],
]
```

The `_item` key separates arguments for the collection field itself (`page`) from arguments for the items within the collection (`total_amount.decimals`).

### Code API usage

Code API consumers can pass field arguments directly:
```php
$order = $getOrder->execute(42, _field_arguments: [
    'total_amount' => ['decimals' => 4],
]);
```

Or simply omit them to use defaults:
```php
$order = $getOrder->execute(42);
```

## 11. Pagination (Cursor Connections)

Paginated collections use the **Relay-style cursor connections** pattern.

### Built-in types

These types live in `src/Api/Pagination/` and are provided by the framework:

```php
namespace Automattic\WooCommerce\Api\Pagination;

class Connection {
    /** @var Edge[] */
    public array $edges;

    /** @var object[] The raw nodes without cursor wrappers. */
    public array $nodes;

    public PageInfo $page_info;

    public int $total_count;
}

class Edge {
    public string $cursor;
    public object $node;
}

class PageInfo {
    public bool $has_next_page;
    public bool $has_previous_page;
    public ?string $start_cursor;
    public ?string $end_cursor;
}
```

### Usage in queries

```php
#[Description('List orders with cursor-based pagination.')]
#[RequiredCapability('read_shop_orders')]
class ListOrders {
    #[ConnectionOf(Order::class)]
    public function execute(
        #[Description('Return the first N results.')]
        ?int $first = null,
        #[Description('Return the last N results.')]
        ?int $last = null,
        #[Description('Return results after this cursor.')]
        ?string $after = null,
        #[Description('Return results before this cursor.')]
        ?string $before = null,
        #[Description('Filter by order status.')]
        ?OrderStatus $status = null
    ): Connection {
        // Implementation builds and returns a Connection object.
    }
}
```

### `#[ConnectionOf(Type::class)]` attribute

Applied to the `execute` method, this attribute tells the build script:
1. The return type is logically `Connection` but the node type is `Type`.
2. The build script generates `TypeConnection` and `TypeEdge` GraphQL types in the schema.
3. `$first`, `$last`, `$after`, `$before` parameters are recognized as standard pagination arguments.

### Usage in output types (sub-collections)

Output type properties can also be connections:

```php
class Order {
    #[Description('The line items in this order.')]
    #[ConnectionOf(LineItem::class)]
    public Connection $line_items;
}
```

### Cursor encoding

Cursors are opaque strings. The recommended implementation is base64-encoded identifiers (e.g., `base64_encode("order:$id")`), but the encoding is an implementation detail not exposed to API consumers.

## 12. Custom Scalar Types

Custom scalar types represent values serialized as primitives but with specific semantics.

Custom scalars are defined as classes in `src/Api/Scalars/`:

```php
namespace Automattic\WooCommerce\Api\Scalars;

#[Description('An ISO 8601 encoded date and time string.')]
class DateTime {
    /**
     * Serialize a PHP value to the scalar's transport format.
     */
    public static function serialize(mixed $value): string {
        if ($value instanceof \DateTimeInterface) {
            return $value->format(\DateTimeInterface::ATOM);
        }
        return (string) $value;
    }

    /**
     * Parse a value received from a client (variable or literal).
     */
    public static function parse(string $value): \DateTimeImmutable {
        return new \DateTimeImmutable($value);
    }
}
```

### Usage

Reference custom scalars via the `#[ScalarType(DateTime::class)]` attribute on properties whose PHP type is a primitive but whose GraphQL type should be the custom scalar:

```php
class Order {
    #[Description('The date the order was created.')]
    #[ScalarType(DateTime::class)]
    public string $date_created;
}
```

### Rules

1. Custom scalar classes must have static `serialize` and `parse` methods.
2. The `#[ScalarType]` attribute is needed because the PHP type (`string`) differs from the GraphQL type (`DateTime`).
3. The build script generates the corresponding `GraphQL\Type\Definition\CustomScalarType` in the schema.

## 13. Authentication & Authorization

### Mechanism

Authentication leverages WordPress's built-in mechanisms (cookies, application passwords, etc.). Authorization uses WordPress capabilities via the `#[RequiredCapability]` attribute.

### `#[RequiredCapability('capability_name')]`

Applied to query/mutation classes to restrict access:

```php
#[RequiredCapability('manage_woocommerce')]
class GetShopSettings {
    public function execute(): ShopSettings { ... }
}
```

### Rules

1. **Every query and mutation class MUST have a `#[RequiredCapability]` attribute**, either directly or inherited (see below). If no capability can be resolved, the build script reports an error.
2. If a query should be publicly accessible, use `#[PublicAccess]` instead (mutually exclusive with `RequiredCapability`).
3. **Multiple `#[RequiredCapability]` attributes** can be applied to the same class. They are equivalent to listing all capabilities in a single attribute. The user must have ALL listed capabilities.
4. When the current user lacks the required capability, the generated GraphQL resolver returns a standard GraphQL error with the message "You do not have permission to perform this action." and an `UNAUTHORIZED` error code in the extensions.
5. The capability check happens before the `execute` method is called.

### Inheritance

If a query/mutation class does not have its own `#[RequiredCapability]` attribute, the build script looks for one in:
- Parent classes (upward through the inheritance chain)
- Implemented PHP interfaces
- Used PHP traits

If multiple `#[RequiredCapability]` attributes are found across the inheritance/implementation chain, **all** capabilities from all sources are required (they are accumulated, not overridden).

```php
// Trait providing a base capability requirement
#[RequiredCapability('manage_woocommerce')]
trait AdminAccess {}

// Parent class with its own requirement
#[RequiredCapability('read_shop_orders')]
abstract class BaseOrderQuery {}

// This class requires BOTH manage_woocommerce AND read_shop_orders AND edit_shop_orders
#[RequiredCapability('edit_shop_orders')]
class UpdateOrder extends BaseOrderQuery {
    use AdminAccess;
    public function execute(int $id, UpdateOrderInput $input): Order { ... }
}
```

## 14. Error Handling

### ApiException

A dedicated exception class in `src/Api/ApiException.php` for errors that should be surfaced to the API client:

```php
namespace Automattic\WooCommerce\Api;

class ApiException extends \RuntimeException {
    private string $error_code;
    private array $extensions;

    public function __construct(
        string $message,
        string $error_code = 'INTERNAL_ERROR',
        array $extensions = [],
        int $status_code = 500,
        ?\Throwable $previous = null
    ) {
        parent::__construct($message, $status_code, $previous);
        $this->error_code = $error_code;
        $this->extensions = $extensions;
    }

    public function getErrorCode(): string { return $this->error_code; }
    public function getExtensions(): array { return $this->extensions; }
    public function getStatusCode(): int { return $this->getCode(); }
}
```

Note: the `$status_code` parameter is intentionally network-agnostic (not named `$http_status`) since `ApiException` is part of the pure code API.

### Behavior

| Exception type | Client receives |
|---|---|
| `ApiException` | The exception message + error code + extensions |
| `\InvalidArgumentException` | The exception message + `INVALID_ARGUMENT` code |
| Any other exception | Generic "An unexpected error occurred." + `INTERNAL_ERROR` code |

In all cases, the error follows the GraphQL errors specification format:

```json
{
  "errors": [
    {
      "message": "Order not found.",
      "extensions": {
        "code": "NOT_FOUND",
        "order_id": 999
      }
    }
  ]
}
```

### Debug mode

Full error details (including the actual exception message and stack trace) are included in the `extensions.debug` field when **any** of the following conditions are met:

1. `WP_DEBUG` is enabled **and** the current user is an administrator.
2. The current user is an administrator **and** the request query string contains `_debug=1`.

## 15. Dependency Injection

Command classes (queries and mutations) are resolved via WooCommerce's existing `RuntimeContainer` (reachable via `wc_get_container()`). The container resolves classes by their full name as singletons. No manual registration or service providers are needed.

Dependencies are injected via the `init` method, following WooCommerce's DI convention. The `init` method **must be `final`**.

```php
class GetOrder {
    private OrderRepository $order_repo;

    final public function init(OrderRepository $order_repo): void {
        $this->order_repo = $order_repo;
    }

    public function execute(int $id): ?Order {
        return $this->order_repo->find($id);
    }
}
```

Code API consumers resolve commands from the container:
```php
$order = wc_get_container()->get(GetOrder::class)->execute(42);
```

## 16. Attributes Reference

All attribute classes live in `Automattic\WooCommerce\Api\Attributes` namespace. They are part of the public API surface (extensions can use them) and are included in the WooCommerce build package.

API classes reference attributes via standard PHP `use` statements:

```php
use Automattic\WooCommerce\Api\Attributes\Description;
use Automattic\WooCommerce\Api\Attributes\RequiredCapability;
use Automattic\WooCommerce\Api\Attributes\Parameter;
// etc.
```

| Attribute | Applies to | Purpose |
|---|---|---|
| `#[Description('...')]` | Classes, properties, methods, method params, enum cases | Human-readable description for GraphQL schema |
| `#[Name('...')]` | Classes, properties, methods, method params, enum cases | Override the default GraphQL name |
| `#[RequiredCapability('...')]` | Query/Mutation classes, parent classes, interfaces, traits | WordPress capability required to execute |
| `#[PublicAccess]` | Query/Mutation classes | Allow unauthenticated access (mutually exclusive with `RequiredCapability`) |
| `#[ArrayOf(type)]` | Properties, method params, method return | Specify the element type for `array` typed values. Accepts `SomeClass::class` or `'int'`/`'float'`/`'string'`/`'bool'`. |
| `#[ConnectionOf(Type::class)]` | `execute` methods, properties | Declare a cursor connection with the specified node type |
| `#[ScalarType(Type::class)]` | Properties | Map a primitive PHP type to a custom GraphQL scalar |
| `#[Deprecated('reason')]` | Properties, enum cases | Mark as deprecated in the GraphQL schema |
| `#[Parameter(...)]` | Output type properties | Declare a field argument (see section 10) |
| `#[ParameterDescription(name, desc)]` | Output type properties | Provide a long description for a field argument (alternative to `description` in `#[Parameter]`) |
| `#[Ignore]` | Query/Mutation classes, DTO classes, DTO properties | Exclude from the GraphQL schema entirely |

### `#[Ignore]` attribute

When applied to:
- A **query/mutation class**: the class is not exposed as a GraphQL query/mutation.
- A **DTO class** (output type or input type): the class is not available in the GraphQL schema.
- A **DTO property**: the property is not included as a GraphQL field.

**Build-time validation**: if a non-ignored entity references an ignored entity (e.g., a non-ignored query returns an ignored output type, or a non-ignored output type has a property of an ignored type), the build script reports an error.

## 17. Build Script Behavior

The build script lives in `src/Internal/Api/Scripts/` and is **excluded from the WooCommerce build package** (along with `Templates/`).

### Input

All PHP classes in `src/Api/` (recursively).

### Process

1. **Scan** all classes using PHP reflection. Attribute classes in `src/Api/Attributes/` are autoloaded normally, so attributes resolve correctly via the standard `use` statements present in each API class.
2. **Classify** each class by its directory: Queries, Mutations, Types, InputTypes, Enums, Interfaces, Scalars, Pagination, Attributes.
3. **Validate** all rules:
   - Type constraints (parameters, return types, properties use only allowed types).
   - Required attributes (`RequiredCapability` or `PublicAccess` on all queries/mutations, resolved through inheritance).
   - No non-ignored entity references an ignored entity.
   - `Parameter` and `ParameterDescription` not both used for the same parameter name.
   - Naming uniqueness (no two GraphQL entities with the same name).
4. **Generate** code in `src/Internal/Api/Autogenerated/`:
   - `GraphQLTypes/` — one PHP file per output type, input type, enum, interface, and scalar, each creating the corresponding `webonyx/graphql-php` type object.
   - `GraphQLQueries/` — one PHP file per query, defining the resolver that wires capability checks → DI container resolution → `execute` invocation → result mapping.
   - `GraphQLMutations/` — same as above but for mutations.
   - `RootQueryType.php` — aggregates all query fields into the root GraphQL `Query` type.
   - `RootMutationType.php` — aggregates all mutation fields into the root GraphQL `Mutation` type.
   - `api_generation_date.txt` — timestamp of the generation.

### Running the build

```sh
pnpm run build:api
```

### Staleness check

The WooCommerce build script (`pnpm run build:zip`) checks if any file in `src/Api/` is newer than `Autogenerated/api_generation_date.txt`. If so, it aborts with a message instructing the developer to run `pnpm run build:api` first.

## 18. GraphQL Endpoint

The `GraphQLController.php` (manually maintained in `src/Internal/Api/`) registers a single WordPress REST route:

```
POST /wp-json/wc/v4/graphql
```

### PHP version check

Before processing any request, the controller checks the PHP version. If the server is running PHP < 8.1, it returns a fixed error response:

```json
{
  "errors": [
    {
      "message": "The GraphQL API is not available on this server."
    }
  ]
}
```

In debug mode (admin user with `_debug=1` in query string, or `WP_DEBUG` enabled for admin users), the error includes the actual reason and the server's PHP version.

### Request format

Request body:
```json
{
  "query": "query { GetOrder(id: 42) { id total_amount status } }",
  "variables": { }
}
```

### Processing

The controller:
1. Checks PHP version (>= 8.1 required).
2. Loads the generated schema from `Autogenerated/`.
3. Parses the GraphQL query.
4. Executes it against the schema (which handles capability checks, DI resolution, field argument extraction, and method invocation).
5. Returns the result in standard GraphQL response format.

```php
// src/Api/Mutations/CreateWebhook.php

namespace Automattic\WooCommerce\Api\Mutations;

use Automattic\WooCommerce\Api\Attributes\Description;
use Automattic\WooCommerce\Api\Attributes\RequiredCapability;
use Automattic\WooCommerce\Api\InputTypes\CreateWebhookInput;

#[Description('Create a new webhook.')]

        $core = new \WC_Webhook();
        $core->set_name($input->name);
        $core->set_topic($input->topic);
```

```php

namespace Automattic\WooCommerce\Api\Types;

use Automattic\WooCommerce\Api\Attributes\ArrayOf;
use Automattic\WooCommerce\Api\Attributes\Description;
use Automattic\WooCommerce\Api\Attributes\Parameter;
use Automattic\WooCommerce\Api\Attributes\ParameterDescription;
use Automattic\WooCommerce\Api\Enums\OrderStatus;
use Automattic\WooCommerce\Api\Interfaces\HasId;

#[Description('Represents a WooCommerce order.')]
class Order {
    use HasId;

    #[Description('The total amount of the order.')]
    #[Parameter(name: 'decimals', type: 'int', default: 2, description: 'Decimal places to round to.')]
    public float $total_amount;

    #[Description('The current status of the order.')]
    public OrderStatus $status;

    #[Description('Coupons applied to this order.')]
    #[ArrayOf(AppliedCoupon::class)]
    #[Parameter(name: 'page', type: 'int', default: 1)]
    #[ParameterDescription('page', 'Page number of the results to fetch.')]

// src/Api/Queries/GetOrder.php

namespace Automattic\WooCommerce\Api\Queries;

use Automattic\WooCommerce\Api\Attributes\Description;
use Automattic\WooCommerce\Api\Attributes\RequiredCapability;
use Automattic\WooCommerce\Api\Enums\OrderStatus;
use Automattic\WooCommerce\Api\Types\Order;

#[Description('Retrieve an order by ID.')]
#[RequiredCapability('read_shop_orders')]
class GetOrder {
    public function execute(
        #[Description('The order ID.')]
        int $id,
        ?array $_field_arguments = null
    ): ?Order {
        $wc_order = wc_get_order($id);
        if (!$wc_order) {
            return null;
        }

        $order = new Order();
        $order->id = $wc_order->get_id();
        $order->status = OrderStatus::from($wc_order->get_status());

        // Apply field argument for total_amount
        $decimals = $_field_arguments['total_amount']['decimals'] ?? 2;
        $order->total_amount = round((float) $wc_order->get_total(), $decimals);

        // Apply field argument for applied_coupons pagination
        $page = $_field_arguments['applied_coupons']['page'] ?? 1;
        $all_coupons = $this->load_coupons($wc_order);
        $order->applied_coupons = array_slice($all_coupons, ($page - 1) * 10, 10);

        return $order;
    }

    // Additional public method for code API convenience (ignored by GraphQL).
    public function get_order_total(int $id, int $decimals = 2): ?float {
        $order = $this->execute($id, ['total_amount' => ['decimals' => $decimals]]);
        return $order?->total_amount;
    }
}
```

```graphql
        first: Int

    GetOrder(id: Int!): Order

    id: Int!
}

interface WebhookDefinition {
    name: String!
    topic: String!
    delivery_url: String!
    secret: String

    secret: String
    status: WebhookStatus!
    failure_count: Int!

    id: Int!

    cursor: String!
    node: Webhook!

type PageInfo {

    end_cursor: String

}
```
