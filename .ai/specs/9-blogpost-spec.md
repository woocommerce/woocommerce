# Blog post specification

Now I want you to write a blog post explaining this project.

For context: this code+GraphQL API implementation is a prototype that may or may not become the basis for a real WooCommerce feature (I'd like the former to be the case). The post is to be published in an internal company blog. I'd like it to be compelling, but not overly long or pedantic. This is not the first project related to this subject I do anyway (see the documents listed in "Prior art" in .ai/specs/PLAN.md) so the motivation and arguments for such a dual API have been laid out already company-wide.

Here's an suggested outline for the blog post, including suggested content for each section. This is just a guideline, feel free to reorder content as you see fit, and to add new sections/new content to cover whatever I may have missed. Use both the implemented code (everything in the working tree) and the specs in .ai/specs for guidance if you need. Ask me before starting if something is not clear.

Write the result to .ai/specs/blogpost-spec.md

1. Motivation

Mostly a reference to the documents listed in "Prior art" in .ai/specs/PLAN.md (just list the documents and I'll add links to the corresponding internal blog posts later), but also include a brief, very summarized explanation of why a combo of authoritative code API + autogenerated GraphQL API is convenient (in general, and for WooCommerce in particular).

2. Basic structure

- There's an authoritative code API that even though conceptually uses GraphQL concepts (queries, mutations, types, connections...) it's actually GraphQL-agnostic and can be used on its own by extensions and by WooCommerce core.
- The code API uses the command pattern (link to Wikipedia or similar for the concept).
- There's an autogenerated GraphQL API (plus some fixed supporting code) that's for internal usage only and depends on the webonyx/php-graphql package.
- Under normal circumstances (so with the exception of failures in the infrastructure itself) the GraphQL API code is to be ignored by developers, "it just works", and the focus is on the code API.
- PHP 8.1+ only, explain why (advanced PHP features with enums being the most prominent, and WooCommerce will require 8.1 at some point in the future anyway) and mention the mechanisms in place to reject usage in PHP 7 and 8.0.
- Directory structure for `src/Api` and `src/Internal/API`, first in the form of an ASCII tree, then a short description (list-style) of what does each directory hold.
- Code sniffer exclusions in place and the motivation for them.

3. HTTP infrastructure

- The fixed GraphQL API endpoint.
- POST and GET support, limitations of the GET endpoint.
- Example POST query with curl, including separate GraphQL arguments.

4. Development cycle

- Manual development of the code API + generation of the GraphQL API via `pnpm run build:api [--no-linter]`.
- Make it clear that `src/Internal/API` is NOT to be touched unless some part of the infrastructure needs fixes or tweaks. 
- Generation date based check via `pnpm run build:api:check`, manually and via CI check.

5. Rules, convention and configuration

- Rules for the code API (including where each kind of class goes, and allowed arguments and return types for class methods).
- The code API allows arbitrary subdirectory nesting inside the predefined directories for better organization.
- Which conventions are in place: class placements, class/method/parameter namings, etc; and how these translate to GraphQL.
- PHP subclasses/interfaces/traits can be freely used beyond what's in the conventions (e.g. common fields for several input types can be coalesced in a base class or trait, even though in the GraphQL side they will become full classes with repeated fields).
- How attributes can be used to override the conventions, including the `Ignore` attribute.

6. Interfaces/traits

- How GraphQL interfaces are implemented in the form of PHP traits (and why).
- The `ReturnType` attribute for queries/mutations whose return type is an interface.
- GraphQL fragments, how they match the usage of interfaces in the code API.

7. Pagination and connections

- Link to a web site describing the relay pattern we use (and short explanation of how it works), mention that it's an established standard in the GraphQL world.
- How it's used: the `Connection` attribute and the supporting classes.
- How the code API can either use supporting classes or do everything on its own, pros and cons of each approach.

8. The `$_query_info` argument

- Why is it convenient, and even mandatory in the cases of parameters accepting fields.
- How to add it to queries in the code API.
- Example usages, simple and complex (including fragments and nested parameter arguments); a query for variable products with fragments and pagination for the variations is a good candidate.

8. Error handling

- What happens when something goes wrong.
- Existing dedicated exception classes, how exceptions (of these types and not) are handled.
- The debug mode: how/when it's activated, what does it change in the error responses.

9. Security

- Authentication is to be done via application passwords or via regular user/password combo, subject to the standard WordPress REST API limitations (SSL only, except in local environments for application passwords).
- The `RequiresCapability` and `PublicAccess` attributes for authorization.
- Inheritance of the attributes, and disabling them with the `Ignore` attribute.
- The `authorize` method, what happens when both this method and the attributes (explicit or inherited) are present.

10. Caching

- Why caching the parsed requests is important.
- Caching mechanisms in place: WordPress' object cache and Apollo APQ.
- The importance of using query arguments to keep the requests fixed and cacheable.
- Example usage of the Apollo APQ part.

11. What's implemented

- The coupons and products queries/mutations, with its shortcomings (most notably, `CreateProduct` can create only simple products).
- Example queries, including fragments usage and field arguments.
- How the queries in place demonstrate the implemented features (briefly, list-style).

12. Possible future improvements

- A "watch" mode for the build script (scans filesystem changes).
- Configuration (a dedicated WooCommerce configurtation page): enable/disable the GraphQL endpoint, configure endpoint URL, enable/disable GET requests, enable/disable caching (each caching mechanism separately).
- OPcache-based caching, how would it work, how it would be beneficial, how would it combine with the other types of caching.
- What parts of WooCommerce would be good candidates for extending the API, with mobile applications as primary clients of the GraphQL part in mind.
- Far-fetched and very speculative but good food for thought: gradually deprecate the current WooCommerce code API (especially the part in `Includes/`) and replace it with this new code API, even for internal WooCommerce usage; also we could decide that any new non-internal code that gets added to WooCommerce becomes part of the code API (instead of going into other places in `src/`). This would ensure that we take good care when designing the public surface of WooCommerce, as now the code API (all of it) would de-facto be also the remote (GraphQL) API.

REMEMBER: ask me if you think I'm missing something, if anything is not clear, or if there's something wrong in what I wrote.
