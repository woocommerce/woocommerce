# WooCommerce GraphQL API - Build Process Specification (Stage 3)

This document specifies when and how the GraphQL infrastructure code is generated, how it integrates with the WooCommerce build pipeline, and how staleness is detected and enforced.

References:
- Stage 1: `stage1-code-api-spec-v2.md` (Code API specification)
- Stage 2: `stage2-supporting-code-spec.md` (Supporting code specification)

---

## 1. Overview

The GraphQL infrastructure code in `src/Internal/Api/Autogenerated/` is **generated at development time** by an explicit command, **committed to source control**, and **shipped as part of the WooCommerce package**. It is NOT generated at runtime or during the package build.

This means:

- Developers run the build script manually after modifying code API classes.
- The generated code is reviewed and committed like any other code.
- The package build (`pnpm run build:zip`) only verifies that the generated code is up to date — it does not regenerate it.
- CI checks enforce that the committed generated code matches the current code API.

---

## 2. Commands

### 2.1. `pnpm run build:api`

Regenerates all GraphQL infrastructure code. This is the primary command developers use.

**When to run**: After any change to files in `src/Api/` (adding, modifying, or deleting queries, mutations, types, enums, interfaces, scalars, or attributes).

**What it does** (in order):

1. Loads the PHP autoloader (`vendor/autoload.php`). Note: `src/Api/` uses PSR-4 autoloading, so newly added classes are discoverable without re-dumping the autoloader. The autoloader dump at step 8 is for the generated classes in `Autogenerated/`, which are wiped and recreated during the build.
2. Scans all PHP classes in `src/Api/` via reflection.
3. Classifies, validates, and extracts metadata (see Stage 2, sections 2.3–2.5).
4. Deletes the entire `src/Internal/Api/Autogenerated/` directory.
5. Recreates the directory structure:
   ```
   Autogenerated/
   ├── GraphQLTypes/
   │   ├── Output/
   │   ├── Input/
   │   ├── Enums/
   │   ├── Interfaces/
   │   ├── Scalars/
   │   └── Pagination/
   ├── GraphQLQueries/
   └── GraphQLMutations/
   ```
6. Generates all files (see Stage 2, sections 3–6).
7. Writes `api_generation_date.txt` with the current Unix timestamp.
8. Regenerates the PHP autoloader (`composer dump-autoload`).
9. Prints a summary: number of queries, mutations, types, etc. generated, and any warnings.

**Exit codes**:
- `0`: Success.
- `1`: Validation error (with details printed to stderr).
- `2`: Environment error (missing dependencies, wrong PHP version, etc.).

**Implementation**: The `pnpm run build:api` script in `package.json` invokes:

```json
{
  "build:api": "php src/Internal/Api/Scripts/build-api.php"
}
```

### 2.2. `pnpm run build:api:check`

Checks whether the generated code is up to date **without regenerating it**. This is used by CI and the package build.

**What it does**:

1. Runs the staleness check (see section 3).
2. If stale: prints an error message and exits with code `1`.
3. If up to date: prints confirmation and exits with code `0`.

**Implementation**:

```json
{
  "build:api:check": "php src/Internal/Api/Scripts/check-api-staleness.php"
}
```

The check script:

```php
// src/Internal/Api/Scripts/check-api-staleness.php

require_once __DIR__ . '/../../../../vendor/autoload.php';

use Automattic\WooCommerce\Internal\Api\Scripts\StalenessChecker;

if (StalenessChecker::isStale()) {
    fwrite(STDERR, "ERROR: Generated GraphQL API code is out of date.\n");
    fwrite(STDERR, "Run 'pnpm run build:api' to regenerate.\n");
    exit(1);
}

echo "GraphQL API code is up to date.\n";
exit(0);
```

## 3. Staleness Detection

### 3.1. Mechanism

The staleness check compares the modification time of every `.php` file in `src/Api/` against the timestamp stored in `src/Internal/Api/Autogenerated/api_generation_date.txt`.

**Stale if any of these are true**:
- `api_generation_date.txt` does not exist.
- Any `.php` file in `src/Api/` (recursively) has an `mtime` newer than the timestamp in `api_generation_date.txt`.

**Not stale**: All `.php` files in `src/Api/` have `mtime` older than or equal to the generation timestamp.

### 3.2. Limitations

- The staleness check is timestamp-based, not content-based. Touching a file without changing it will trigger a false positive. This is acceptable — running `build:api` on unchanged code is a no-op in terms of output (the generated code will be identical).
- Deleting a code API class makes the generated code stale, but the deleted file's timestamp is no longer available. The staleness check handles this indirectly: the `api_generation_date.txt` will be older than the deletion event only if other files were also modified. For safety, **the build script also validates that all generated resolvers and types still reference existing code API classes** during `build:api:check` — if a resolver references a deleted class, the check fails.

### 3.3. Enhanced staleness check (optional future improvement)

A more robust approach would store a hash of the `src/Api/` directory contents alongside the timestamp. This is not required for the initial implementation but could be added if false negatives become a problem.

## 4. Integration with WooCommerce Build Pipeline

### 4.1. Package build (`pnpm run build:zip`)

The WooCommerce package build script must include a staleness check step **before** creating the distributable package:

```
pnpm run build:zip
├── ... existing build steps ...
├── pnpm run build:api:check    ← added step
│   ├── If stale → abort with error message
│   └── If up to date → continue
├── ... remaining build steps ...
└── Create .zip
```

This ensures that no package is shipped with outdated GraphQL infrastructure.

### 4.2. Excluded files

The following files and directories are **excluded from the WooCommerce package** (they are development-time only):

- `src/Internal/Api/Scripts/` — build script, staleness checker, CLI entry points
- `src/Internal/Api/Templates/` — code generation templates

Everything else in `src/Internal/Api/` is included, particularly:
- `src/Internal/Api/Autogenerated/` — all generated code
- `src/Internal/Api/GraphQLController.php` — endpoint handler
- `src/Internal/Api/Main.php` — initialization

And the entire `src/Api/` directory is included (it's the public code API).

### 4.3. Autoloader

The generated classes follow PSR-4 and are autoloaded by Composer. After running `build:api`, the autoloader is regenerated automatically (step 8 in section 2.1). The `composer.json` autoload configuration covers the `Autogenerated/` namespace:

```json
{
  "autoload": {
    "psr-4": {
      "Automattic\\WooCommerce\\Internal\\Api\\Autogenerated\\": "src/Internal/Api/Autogenerated/"
    }
  }
}
```

(This is in addition to the existing WooCommerce autoload configuration.)

## 5. Pre-commit Hook

The staleness check should run as a **pre-commit hook** to prevent committing stale generated code. Since the check only compares file timestamps, it adds negligible overhead.

```bash
# In .husky/pre-commit (or equivalent):
pnpm run build:api:check
```

This catches the most common mistake: modifying files in `src/Api/` without running `pnpm run build:api`. The hook runs unconditionally (not scoped to `src/Api/` changes) because the check is fast and also catches edge cases like accidentally deleted generated files.

Note that the pre-commit hook catches "forgot to regenerate" but not "regenerated but forgot to stage the generated files". The CI diff check (section 6.2) covers that case.

## 6. CI Integration

### 6.1. CI check

CI should run `pnpm run build:api:check` on every pull request that modifies files in `src/Api/`. If the check fails, the PR cannot be merged.

A more thorough CI check can also:
1. Run `pnpm run build:api` to regenerate.
2. Run `git diff --exit-code src/Internal/Api/Autogenerated/` to verify the committed generated code matches what the script produces.

This catches cases where a developer ran `build:api` but with a different PHP version or configuration that produced different output.

### 6.2. Recommended CI step

```yaml
# In the CI workflow:
- name: Check GraphQL API code is up to date
  run: |
    pnpm run build:api
    git diff --exit-code src/Internal/Api/Autogenerated/
```

If the diff is non-empty, the step fails with a clear indication of which files differ.

## 7. Developer Workflow

### 7.1. Adding or modifying a query/mutation/type

1. Edit files in `src/Api/`.
2. Run `pnpm run build:api`.
3. Review the generated changes in `src/Internal/Api/Autogenerated/`.
4. Commit both the code API changes and the generated code together.

### 7.2. Reviewing generated code

Generated code is committed and shows up in diffs. Reviewers should:
- Focus review on the `src/Api/` changes (the authoritative code).
- Verify the generated code looks reasonable but treat it as derived output.
- If the generated code looks wrong, the issue is in the build script or templates, not in the generated files.

### 7.3. Resolving conflicts in generated code

If a merge conflict occurs in `Autogenerated/`:
1. Accept either version (it doesn't matter which).
2. Run `pnpm run build:api` to regenerate from the merged `src/Api/`.
3. Commit the regenerated files.

### 7.4. Quick reference

| I want to... | Command |
|---|---|
| Regenerate after changing code API | `pnpm run build:api` |
| Check if generated code is up to date | `pnpm run build:api:check` |
| Fix merge conflicts in generated code | `pnpm run build:api` |

## 8. Error Messages

The build script provides clear, actionable error messages:

| Situation | Message |
|---|---|
| Missing `#[RequiredCapability]` | `Error: Query "GetOrder" has no RequiredCapability attribute (directly or inherited) and no PublicAccess attribute.` |
| Type constraint violation | `Error: Property "Order::$status" has type "string" but references enum "OrderStatus". Use the enum type directly.` |
| Missing `#[ArrayOf]` | `Error: Property "Order::$line_items" is typed as "array" but has no #[ArrayOf] attribute.` |
| Name collision | `Error: GraphQL name "Order" is used by both "Api\Types\Order" and "Api\Types\Legacy\Order".` |
| Ignored reference | `Error: Non-ignored query "GetOrder" returns ignored type "Order".` |
| Parameter/ParameterDescription conflict | `Error: Property "Order::$total_amount" has both description in #[Parameter] and #[ParameterDescription] for parameter "decimals".` |
| Staleness (during build:api:check) | `ERROR: Generated GraphQL API code is out of date. Run 'pnpm run build:api' to regenerate.` |
| PHP version too old (build script) | `Error: PHP 8.1 or later is required to run the API build script. Current version: 7.4.33.` |

## 9. Summary

| Aspect | Detail |
|---|---|
| **When is code generated?** | Manually by the developer, via `pnpm run build:api` |
| **Is generated code committed?** | Yes, committed to source control |
| **Is generated code shipped?** | Yes, included in the WooCommerce package |
| **Is code generated at runtime?** | No |
| **Is code generated during package build?** | No, only a staleness check runs |
| **How is freshness enforced?** | `build:api:check` in pre-commit hook, CI, and package build |
| **How are conflicts resolved?** | Regenerate with `build:api` after merging `src/Api/` |
