Surprisingly for approximately nobody, I have dedicated my last hack week project to further explore the possibility of adding a GraphQL API to WooCommerce core. More precisely, I have developed a working prototype for a new WooCommerce API built around two ideas: an **authoritative code API** that uses plain PHP classes to define queries, mutations, and data types; and an **auto-generated GraphQL layer** that exposes those same classes over HTTP, with zero additional effort from developers.

A significant difference this time is that I've used an AI agent to assist me with the development. This has allowed me to come up with a functional (incomplete, but functional) prototype in the time frame of the hack week project. More details at the end of this post.

[Here's the pull request](https://github.com/woocommerce/woocommerce/pull/63772) if you want to skip straight to the juicy stuff.

## Motivation

This project builds on ideas already explored in previous hack week projects:

- *MVC based REST API* (June 2023): Convention + attribute-based configuration, automated infrastructure generation, and error handling.
- *MVC based REST API, documentation edition* (September 2023): Extending the same ideas to automated documentation generation.
- *One API to query them all* (December 2023): The command pattern, mapping data types to classes, field arguments, and build-time infrastructure generation.
- *WooA! WooCommerce (new/unified) API* (March 2024): Concrete rules for naming, directory structures, attributes, and the behavior of the build script.

The core idea hasn't changed: WooCommerce would greatly benefit from a clean, public code API that internal code and extensions can both rely on. If that code API is designed around GraphQL-friendly concepts (typed queries, mutations, connections, field arguments), then generating a real GraphQL endpoint from it becomes nearly free. The result is a single source of truth used in two ways: in-process PHP calls for extensions and core, and remote GraphQL calls for mobile apps and external clients.

An extension of this idea that has also been explored in the past is a dual REST + GraphQL API, both equally autogenerated from the base code API. However, in this case I decided to limit the scope to GraphQL only, due to the time constraints of hack weeks and to keep the whole thing manageable.

## Basic structure

At its core, this project implements two basic components:

- **The code API** lives under `src/Api/`. It uses the [command pattern](https://en.wikipedia.org/wiki/Command_pattern): each query or mutation is a class with a single `execute()` method. Data types are DTO classes with typed public properties. The code API is completely GraphQL-agnostic: it imports nothing from any GraphQL library and can be used on its own by WooCommerce core or by extensions.

- **The GraphQL layer** lives under `src/Internal/Api/`. It consists of auto-generated resolver classes (in `Autogenerated/`) plus a small set of fixed infrastructure classes (the HTTP endpoint, query cache, and AST extractor). This code depends on the [webonyx/graphql-php](https://github.com/webonyx/graphql-php) package.

The important idea here is that the code API is the **authoritative** API, the one manually designed and maintained by developers; while the GraphQL layer is autogenerated and **not** intended to be touched (or even looked at) by developers under normal circumstances: it just works.

### PHP 8.1+ only

The code API makes heavy use of PHP 8.1 features: native enums for GraphQL enum types, typed properties everywhere, union/intersection types in return values, and PHP 8 attributes for declarative configuration. WooCommerce will require PHP 8.1 at some point in the not-so-distant future, so this requirement is not so far-fetched.

To prevent cryptic parse errors on older PHPs (7.4 and 8.0), two guards are in place as part of the internal infrastructure:

- `Main.php` registers a custom autoloader that throws a clear `RuntimeException` ("The WooCommerce Code API requires PHP 8.1 or later") if any class in the `Automattic\WooCommerce\Api\` namespace is loaded on PHP < 8.1.
- `GraphQLController` returns a 500 response with a human-readable message if the endpoint is hit on older PHP.

### Directory structure

```
src/Api/                            ← Public code API (GraphQL-agnostic)
├── Attributes/                     ← PHP 8.1 attributes (#[Description], #[Name], ...)
├── Enums/                          ← Backed enums (ProductStatus, DiscountType, ...)
├── InputTypes/                     ← Input DTOs for mutations/queries
├── Interfaces/                     ← Interface traits (Product, ObjectWithId)
├── Mutations/                      ← Mutation command classes
├── Pagination/                     ← Connection, Edge, PageInfo, PaginationParams
├── Queries/                        ← Query command classes
├── Scalars/                        ← Custom scalars (DateTime)
├── Traits/                         ← Shared traits (RequiresManageWoocommerce)
├── Types/                          ← Output type DTOs
├── Utils/                          ← Mappers, repositories, helpers
├── ApiException.php                ← API-level exception
└── AuthorizationException.php      ← Authorization failure exception

src/Internal/Api/                   ← GraphQL infrastructure (internal)
├── Autogenerated/                  ← Generated code (DO NOT EDIT)
│   ├── GraphQLQueries/             ← Query resolvers
│   ├── GraphQLMutations/           ← Mutation resolvers
│   ├── GraphQLTypes/               ← Type definitions (Output/, Input/, Enums/, ...)
│   ├── RootQueryType.php           ← Schema root query
│   ├── RootMutationType.php        ← Schema root mutation
│   ├── TypeRegistry.php            ← Interface implementor registry
│   └── api_generation_date.txt     ← Timestamp for staleness checks
├── DesignTime/                     ← Build-time code (not shipped in production)
│   ├── Scripts/                    ← ApiBuilder, build-api.php, staleness checker
│   └── Templates/                  ← PHP templates for code generation
├── GraphQLController.php           ← HTTP endpoint handler
├── Main.php                        ← Initialization + PHP version guard
├── QueryCache.php                  ← AST caching + Apollo APQ
└── QueryInfoExtractor.php          ← Extracts query structure from ResolveInfo
```

Key points:

- **`src/Api/`**: This is where developers work. Everything here is public API surface.
- **`src/Internal/Api/Autogenerated/`**: Regenerated by the build script. Committed to source control but never edited by hand.
- **`src/Internal/Api/DesignTime/`**: Build tools and templates. Excluded from the WooCommerce production package.
- **`src/Internal/Api/` (root files)**: Fixed infrastructure that rarely changes.
- Arbitrary subdirectory nesting is allowed inside the predefined directories (e.g., `Queries/Products/`, `Enums/Coupons/`) for better organization.

### Code sniffer exclusions

The code API and its infrastructure don't fit neatly into the existing WooCommerce PHPCS ruleset, so a handful of targeted exclusions are configured in `phpcs.xml`:

- **PHPCompatibility** is disabled for all of `src/Api/` and `src/Internal/Api/`. The code is PHP 8.1+ by design — running PHP compatibility checks against older versions would flag every enum, every typed property, and every attribute as an error.
- **`Squiz.Commenting.VariableComment.Missing`** is suppressed for `Types/`, `InputTypes/`, and `Pagination/`. These are DTO classes where `#[Description]` attributes serve as documentation; requiring a `@var` docblock on every property would be redundant.
- **`base64_encode` / `base64_decode` warnings** are suppressed across `src/Api/`. The `DiscouragedPHPFunctions` rule flags these as "obfuscation", but cursor-based pagination legitimately uses base64 for opaque cursor strings.
- **Reserved keyword parameter names** are allowed in `Attributes/Parameter.php`, which has a `$type` and `$default` parameter: both reserved keywords but unavoidable for an attribute that declares field argument metadata.
- **Autogenerated code** (`src/Internal/Api/Autogenerated/`) suppresses commenting rules, unused parameter warnings, escape output rules, and non-snake-case property access. Generated code doesn't need docblocks, and it interacts with the webonyx library whose objects use camelCase properties.
- **Templates** (`src/Internal/Api/DesignTime/Templates/`) suppress strict types, file headers, commenting, Yoda conditions, `var_export`, and `extract` rules. These are PHP template files that emit PHP code: they need `extract()` for template variables and `var_export()` for generating literal values, and there's really no need to enforce strict typing or Yoda conditions in template output.

## HTTP infrastructure

The GraphQL endpoint is registered as a WooCommerce REST route:

```
POST /wp-json/wc/v4/graphql
GET  /wp-json/wc/v4/graphql
```

Both `POST` and `GET` are supported. `GET` requests have two limitations: mutations are rejected with a `405 METHOD_NOT_ALLOWED` error (per the [GraphQL over HTTP spec](https://graphql.github.io/graphql-over-http/)), and the `variables` and `extensions` parameters must be JSON-encoded strings.

**Example POST request with curl:**

```bash
curl -X POST https://<site base url>/wp-json/wc/v4/graphql \
  -H "Content-Type: application/json" \
  -u "<username>:<application password>" \
  -d '{
    "query": "query GetProduct($id: Int!) { Product(id: $id) { name regular_price(formatted: false) status } }",
    "variables": { "id": 42 }
  }'
```

**Equivalent GET request:**

```bash
curl -G https://<site base url>/wp-json/wc/v4/graphql \
  -u "<username>:<application password>" \
  --data-urlencode 'query=query GetProduct($id: Int!) { Product(id: $id) { name regular_price(formatted: false) status } }' \
  --data-urlencode 'variables={"id":42}'
```

Note the use of GraphQL variables to keep the query string fixed and cacheable; more on this in the caching section.

## Development cycle

The workflow is straightforward:

1. **Write/edit code API classes** in `src/Api/`: queries, mutations, types, enums... as needed.
2. **Generate the GraphQL infrastructure** by running:
   ```bash
   pnpm run build:api           # Full build with linting
   pnpm run build:api --no-linter  # Skip PHP_CodeSniffer (faster iteration)
   ```
3. **Review and commit** both `src/Api/` changes and the regenerated `src/Internal/Api/Autogenerated/` files (don't forget to run `pnpm run build:api` **without** `--no-linter` before committing!)

The build script scans `src/Api/`, reflects on all classes, validates them against the rules, and generates all the GraphQL plumbing: type definitions, query/mutation resolvers, the root types, and the type registry. If validation fails (e.g., a query class is missing an `execute()` method), it prints clear errors and exits with code 1.

**Important:** `src/Internal/Api/` should not be touched manually except for fixing infrastructure bugs. The autogenerated code is, well, autogenerated. The fixed infrastructure (controller, cache, etc.) changes rarely.

### Staleness check

A timestamp-based staleness check is available:

```bash
pnpm run build:api:check
```

This compares `api_generation_date.txt`, a file generated by the build script, against the modification times of all PHP files in `src/Api/`. If any code API file is newer than the last generation, it exits with an error:

```
ERROR: Generated GraphQL API code is out of date.
Run 'pnpm run build:api' to regenerate.
```

This can be integrated into CI and pre-commit hooks to catch forgotten rebuilds.

## Rules, conventions, and configuration

The build script relies on the following conventions, developers working on the code API should always respect them:

### Class placement rules

| Class kind   | Directory            | GraphQL mapping                |
|-------------|----------------------|--------------------------------|
| Queries     | `Queries/`           | Root query fields              |
| Mutations   | `Mutations/`         | Root mutation fields           |
| Output types | `Types/`            | Object types                   |
| Input types  | `InputTypes/`       | Input object types             |
| Enums        | `Enums/`            | Enum types                     |
| Interfaces   | `Interfaces/`       | Interface types                |
| Scalars      | `Scalars/`          | Custom scalar types            |

As already mentioned, arbitrary subdirectories inside these directories are allowed and can be convenient for better organization of the code.

Generic utility classes that don't fit into any of the categories for these directories should be put in the `Utils` directory. Worth noting also that the other directories in `src/Api/` (like `Attributes`, `Pagination`...) are "public infrastructure": intended to be used by code API classes, but not to be touched under normal circumstances. 

### Naming conventions

- **Query/mutation classes** must have an `execute()` method. The GraphQL field name defaults to the class name (e.g., `GetProduct`), overridable with `#[Name('Product')]`.
- **Properties** on output and input types become GraphQL fields, keeping their `snake_case` names.
- **Enum cases** are converted to `SCREAMING_SNAKE_CASE` (e.g., `InStock` → `IN_STOCK`), overridable with `#[Name]`.
- PHP subclasses, abstract base classes, and traits can be freely used for code organization. For instance, `CreateProductInput` extends `BaseProductInput` which defines shared fields: the GraphQL side flattens everything into a single input type with all inherited properties.

### Attributes

The code API uses PHP 8 attributes for configuration that goes beyond conventions:

| Attribute | Purpose |
|-----------|---------|
| `#[Description('...')]` | Human-readable description for any type, field, or parameter |
| `#[Name('...')]` | Override the default GraphQL name |
| `#[Ignore]` | Exclude a class or property from the GraphQL schema |
| `#[ReturnType(Product::class)]` | Declare the interface return type for queries/mutations |
| `#[ConnectionOf(Node::class)]` | Mark a field or query return as a Relay connection |
| `#[Parameter(name: 'formatted', type: 'bool', default: true)]` | Declare a field argument |
| `#[ParameterDescription(...)]` | Add a description to a field argument |
| `#[ArrayOf(Item::class)]` | Declare the element type for array properties |
| `#[ScalarType(DateTime::class)]` | Override the default scalar mapping |
| `#[Unroll]` | Expand a class's properties into flat GraphQL arguments |
| `#[RequiredCapability('...')]` | Require a WordPress capability (repeatable) |
| `#[PublicAccess]` | Mark an operation as publicly accessible |
| `#[Deprecated('reason')]` | Mark a field or enum value as deprecated |

## Interfaces and traits

GraphQL interfaces are represented as PHP **traits**, not PHP interfaces. Why? Because PHP interfaces can't define typed properties, and we need the concrete field definitions (with types, attributes, and all) to live in a single place.

For example, the `Product` interface trait defines all shared product fields:

```php
#[Name('Product')]
#[Description('A WooCommerce product.')]
trait Product {
    use ObjectWithId;

    #[Description('The product name.')]
    public string $name;

    #[Description('The regular price of the product.')]
    #[Parameter(name: 'formatted', type: 'bool', default: true, description: 'Whether to apply currency formatting.')]
    public string $regular_price;

    #[Description('Customer reviews for this product.')]
    #[ConnectionOf(ProductReview::class)]
    public Connection $reviews;

    // ... more fields
}
```

Concrete types then `use` the trait:

```php
#[Description('A simple product.')]
class SimpleProduct {
    use Product;
}

#[Description('A variable product with variations.')]
class VariableProduct {
    use Product;

    #[Description('The product variations.')]
    #[ConnectionOf(ProductVariation::class)]
    #[Parameter(type: PaginationParams::class)]
    public Connection $variations;
}
```

When a query or mutation returns one of these types, it declares the interface via `#[ReturnType]`:

```php
#[ReturnType(Product::class)]
public function execute(int $id): ?object { ... }
```

On the GraphQL side, clients use **inline fragments** to access type-specific fields:

```graphql
query {
  Product(id: 42) {
    name          # from the Product interface
    regular_price
    ...on VariableProduct {
      variations(first: 5) {
        nodes { id }
      }
    }
    ...on ExternalProduct {
      product_url
      button_text
    }
  }
}
```

## Pagination and connections

The API uses the [Relay cursor connection specification](https://relay.dev/graphql/connections.htm), an established standard in the GraphQL world. In a nutshell: collections are returned as "connections" containing `edges` (each wrapping a `node` and a `cursor`), `pageInfo` with `hasNextPage`/`hasPreviousPage`, and a `totalCount`. Clients paginate using `first`/`after` (forward) or `last`/`before` (backward) arguments, referencing a cursor as the starting point.

### Usage in the code API

A query that returns a connection annotates its return type:

```php
#[ConnectionOf(Product::class)]
public function execute(PaginationParams $pagination, ...): Connection { ... }
```

The build script sees `#[ConnectionOf]` and generates the appropriate `ProductConnection` and `ProductEdge` GraphQL types, as well as pagination arguments (`first`, `last`, `after`, `before`) on the query field.

Worth noting that `PaginationParams` has an `#[Unroll]` attribute, which means the build script doesn't expose it as a single input object on the GraphQL side; instead, its properties (`first`, `last`, `after`, `before`) become individual top-level arguments on the query field. The build script also sees `#[ConnectionOf]` and generates the appropriate `ProductConnection` and `ProductEdge` GraphQL types.

For **nested connections** (like `variations` on a `VariableProduct`), the same annotation goes on the property:

```php
#[ConnectionOf(ProductVariation::class)]
#[Parameter(type: PaginationParams::class)]
public Connection $variations;
```

The auto-generated resolver handles pagination automatically by calling `Connection::slice($args)` with the client's pagination arguments.

### Two paths for connection building

The code API supports two approaches:

1. **Full load + slice**: Load all items into a `Connection`, let `slice()` handle pagination in memory. Simple, correct, fine for small collections (e.g., a product's variations).
2. **SQL-level (or WordPress/WooCommerce API level) pagination**: Decode cursors to IDs, apply `WHERE` filters in the database query, fetch only `limit + 1` rows. Efficient for large collections (e.g., `ListProducts` does this).

The `Connection` class also provides a `pre_sliced()` factory for the performance path: when the DB query already applied pagination, this builds a `Connection` marked as already sliced, so subsequent `slice()` calls from auto-generated resolvers become no-ops.

## The `$_query_info` argument

Command classes can optionally receive a `$_query_info` parameter, this is a plain PHP array that describes the structure of the incoming GraphQL query (which fields were requested, with what arguments, including inline fragments).

```php
public function execute(
    int $id,
    ?array $_query_info = null,
): ?object { ... }
```

The underscore prefix signals to the build script that this is an infrastructure parameter (not a GraphQL argument coming from the code API). The system populates it automatically from the GraphQL `ResolveInfo`.

This argument is useful (and sometimes, even mandatory) in the following cases:

- **Performance-oriented queries**: Skip expensive work for fields that weren't requested. For example, `ProductMapper` only loads reviews when the `reviews` field is in the query.
- **Field arguments**: Some fields accept arguments (like `regular_price(formatted: false)`). The command class needs `$_query_info` to read those arguments and adjust its behavior.
- **Connection slicing**: The command class can extract pagination args from a nested connection field and slice the connection explicitly, giving it full control over pagination behavior.

The `$_query_info` array mirrors the shape of the incoming GraphQL query. This is how it's composed:

- A **leaf field** with no arguments and no sub-selection maps to `true`. For example, requesting `name` produces `'name' => true`.
- A **field with sub-selections** maps to a nested associative array. For example, `pageInfo { hasNextPage }` produces `'pageInfo' => ['hasNextPage' => true]`.
- **Field arguments** are stored under the reserved `'__args'` key within the field's array. For example, `regular_price(formatted: false)` produces `'regular_price' => ['__args' => ['formatted' => false]]`.
- **Inline fragments** use a `'...TypeName'` key. For example, `...on VariableProduct { variations { ... } }` produces `'...VariableProduct' => ['variations' => [...]]`.
- **Top-level query arguments** (the arguments passed to the query/mutation itself) are also available under `'__args'` at the root level.

GraphQL variables are resolved before the array is built, so `$_query_info` always contains the final concrete values.

### Example: variable product with fragments and field arguments

Given this query:

```graphql
query {
  Product(id: 99) {
    name
    regular_price(formatted: false)
    ...on VariableProduct {
      variations(first: 2) {
        nodes { id name }
        totalCount
        pageInfo { hasNextPage endCursor }
      }
    }
  }
}
```

The `$_query_info` array looks like:

```php
[
    'name' => true,
    'regular_price' => [
        '__args' => ['formatted' => false],
    ],
    '...VariableProduct' => [
        'variations' => [
            '__args' => ['first' => 2],
            'nodes' => ['id' => true, 'name' => true],
            'totalCount' => true,
            'pageInfo' => ['hasNextPage' => true, 'endCursor' => true],
        ],
    ],
]
```

The command code can then use this directly:

```php
// Read field arguments for price formatting.
$format = $query_info['regular_price']['__args']['formatted'] ?? true;

// Extract pagination args for variations (checking both fragment and direct paths).
$pagination_args = $query_info['...VariableProduct']['variations']['__args']
    ?? $query_info['variations']['__args']
    ?? [];
$connection = $connection->slice($pagination_args);
```

## Error handling

Errors follow the standard GraphQL error format: an `errors` array where each entry has a `message` and an `extensions` object with a machine-readable `code`.

### Exception types

- **`ApiException`**: The primary exception for API-level errors. Accepts a message, error code (e.g., `'NOT_FOUND'`, `'VALIDATION_ERROR'`), optional extensions, and an HTTP status code.
- **`AuthorizationException`**: Extends `ApiException` with pre-configured `UNAUTHORIZED` code and 401 status.
- **`\InvalidArgumentException`**: Caught and wrapped with code `INVALID_ARGUMENT`.
- **Any other `\Throwable`** — Caught and returned as `"An unexpected error occurred."` with code `INTERNAL_ERROR`. The original exception is preserved internally (via `previous`) so that debug mode can expose the details (see below).

### Debug mode

Debug mode activates when:
- `WP_DEBUG` is `true` and the user is an administrator or in a local environment, **or**
- the `_debug=1` query parameter is present and the user is an administrator or in a local environment.

When active, error responses include an additional `extensions.debug` object with the original exception message, file, line, and stack trace. "Local environment" means that either `wp_get_environment_type()` returns `local`, or the host is `localhost` or `127.0.0.1`.

## Security

### Authentication

For authentication we use the standard WordPress REST API mechanisms: [application passwords](https://make.wordpress.org/core/2020/11/05/application-passwords-integration-guide/) or regular username/password credentials via HTTP Basic Auth. The same restrictions apply: application passwords require SSL in production (local environments are exempt), which is a sensible default for any API carrying store data. Since the GraphQL endpoint is registered as a WooCommerce REST route (`/wp-json/wc/v4/graphql`), all of this works out of the box with no additional authentication code.

The existing WooCommerce REST API authentication mechanism (using dedicated consumer key/secret pairs) has been excluded for simplicity, but also because the permissions for these keys are very broad (just read, write or both) and we are using a capabilities-based mechanism for authorization instead (see below).

### Authorization

Every query and mutation must declare its authorization strategy. There are three options:

**1. `#[RequiredCapability]`**: Declares one or more WordPress capabilities required to execute:

```php
#[RequiredCapability('manage_woocommerce')]
#[RequiredCapability('edit_products')]
class CreateProduct { ... }
```

Multiple capabilities use AND logic (all must pass). The attribute is **inheritable** via traits or base classes: for example, `RequiresManageWoocommerce` is a trait with `#[RequiredCapability('manage_woocommerce')]` that any command class can `use`.

**2. `#[PublicAccess]`**: No capability checks at all:

```php
#[PublicAccess]
class GetCoupon { ... }
```

**3. `authorize()` method** — Custom authorization logic with access to the query parameters. Its parameters must be all or a subset of the `execute()` method's parameters (the generated infrastructure passes them automatically):

```php
public function authorize(int $id): bool {
    $post = get_post($id);
    if (current_user_can('manage_woocommerce')) {
        return true;
    }
    return get_current_user_id() === (int) $post->post_author;
}
```

When both `#[RequiredCapability]` (explicit or inherited) and an `authorize()` method are present, capability checks run first: if they pass, `authorize()` is called for fine-grained decisions.

It's possible to apply the `#[Ignore]` attribute to an `authorize()` method and then it won't be used for authorization. This is useful for query classes that inherit the method from a base class or trait, but we want to disregard it and stick to attribute-based authorization only.

The build script validates that every command class has at least one of these three strategies (explicitly, or via inherited attributes or `authorize()` method). Missing authorization is a build error.

## Caching

Parsing a GraphQL query string into an AST is a non-trivial operation. For a production API serving repeated queries (especially from mobile apps sending the same queries with different variables), caching the parsed AST avoids redundant work on every request.

### WordPress object cache

Every parsed query is cached in the WordPress object cache using `wp_cache_get`/`wp_cache_set`. The cache key is `graphql_ast_v15_{sha256_hash}`: the `v15` prefix matches the webonyx/graphql-php major version, so upgrading the library naturally invalidates stale entries. The AST is stored as a plain PHP array (via `DocumentNode::toArray()`) for serialization compatibility.

This works automatically with any persistent object cache backend (Redis, Memcached, etc.).

### Apollo Automatic Persisted Queries (APQ)

The API implements the [Apollo APQ protocol](https://www.apollographql.com/docs/apollo-server/performance/apq/). The flow:

1. **First request**: Client sends the full query + its SHA-256 hash in `extensions.persistedQuery`. The server validates the hash, parses the query, caches it, and returns the result.
2. **Subsequent requests**: Client sends only the hash (no query body). The server looks it up in cache and executes directly.
3. **Cache miss**: If the hash isn't found, the server returns `PERSISTED_QUERY_NOT_FOUND` with HTTP 200 (per Apollo convention; it's a protocol signal, not an error). The client then retries with the full query.

This reduces bandwidth significantly for repeated queries and is particularly well-suited for mobile clients.

**Example: first request (registration):**

```bash
curl -X POST https://<site base URL>/wp-json/wc/v4/graphql \
  -H "Content-Type: application/json" \
  -d '{
    "query": "query { Products(first: 10) { nodes { id name } } }",
    "extensions": {
      "persistedQuery": {
        "version": 1,
        "sha256Hash": "ecf4edb46db40b5132295c0291d62fb65d6759a9eedfa4d5d612dd5ec54a6b38"
      }
    }
  }'
```

**Subsequent request (hash only):**

```bash
curl -X POST https://<site base URL>/wp-json/wc/v4/graphql \
  -H "Content-Type: application/json" \
  -d '{
    "extensions": {
      "persistedQuery": {
        "version": 1,
        "sha256Hash": "ecf4edb46db40b5132295c0291d62fb65d6759a9eedfa4d5d612dd5ec54a6b38"
      }
    }
  }'
```

### Keeping queries fixed

For both caching mechanisms, it's important to use **GraphQL variables** instead of interpolating values into the query string. The query `Product(id: 42)` and `Product(id: 43)` are different strings with different hashes. Using `Product(id: $id)` with `variables: { "id": 42 }` keeps the query string (and its cache key) constant.

## What's implemented

The prototype includes full CRUD operations for **products** and **coupons**:

**Queries:**
- `Product(id)`: Single product by ID, with `authorize()` for fine-grained access control.
- `Products(first, after, ...)`: Paginated product list with filters (status, stock status, search, product type). Uses SQL-level cursor pagination.
- `Coupon(id, code)`: Single coupon by ID or code (public access).
- `Coupons(first, after, ...)`: Paginated coupon list.

**Mutations:**
- `CreateProduct(input)` / `UpdateProduct(input)` / `DeleteProduct(id, force)`
- `CreateCoupon(input)` / `UpdateCoupon(input)` / `DeleteCoupon(id, force)`

**Known limitations:**
- `CreateProduct` can only create simple products (no variable/external product creation).
- Not all WooCommerce product fields are exposed yet.

### Example queries

**List products with pagination and type filter:**

```graphql
query {
  Products(first: 5, product_type: VARIABLE) {
    nodes {
      id
      name
      regular_price(formatted: false)
      stock_status
    }
    totalCount
    pageInfo {
      hasNextPage
      endCursor
    }
  }
}
```

**Get a variable product with fragments and variation pagination:**

```graphql
query {
  Product(id: 99) {
    id
    name
    ...on SimpleProduct {
      regular_price
    }
    ...on VariableProduct {
      variations(first: 3) {
        nodes {
          id
          name
          regular_price(formatted: false)
          selected_attributes { name value }
        }
        pageInfo { hasNextPage endCursor }
        totalCount
      }
    }
    ...on ExternalProduct {
      product_url
      button_text
    }
  }
}
```

**Create a product:**

```graphql
mutation {
  CreateProduct(input: {
    name: "Test Widget"
    regular_price: 29.99
    status: PUBLISH
    description: "A fantastic widget."
    dimensions: { weight: 0.5, length: 10, width: 5, height: 3 }
  }) {
    id
    name
    regular_price
    status
  }
}
```

### Feature coverage

The implemented queries and mutations together demonstrate:

- Command pattern with `execute()` and optional `authorize()`
- Interface traits with inline fragment resolution (`Product` → `SimpleProduct`, `VariableProduct`, `ExternalProduct`)
- Relay cursor connections at both top level (`Products`) and nested level (`variations`, `reviews`)
- Field arguments (`regular_price(formatted: false)`)
- The `$_query_info` parameter for conditional loading and explicit slicing
- Input types with `TracksProvidedFields` for partial updates
- Enums, custom scalars (`DateTime`), and the `#[Deprecated]` attribute
- Multiple authorization strategies across queries and mutations
- `#[Unroll]` for flattening parameter objects into individual GraphQL arguments

## Possible future improvements

- **Unit tests**: this is not an "improvement" as much as it's a missing piece of infrastructure. This would be the first thing to add should we continue working on this project.

- **Watch mode** for the build script: monitor filesystem changes in `src/Api/` and automatically regenerate when files change, for a faster development loop.

- **Configuration page**: A dedicated WooCommerce settings page to: enable/disable the GraphQL endpoint, configure the endpoint URL, enable/disable GET requests, and toggle each caching mechanism independently.

- **OPcache-based caching**: Write parsed ASTs as PHP files (`return [...]`) so that OPcache stores them as compiled bytecode. On cache hit, loading the AST would be nearly free (no parsing, no unserialization; just an opcode fetch). This could layer on top of the existing WP object cache and APQ mechanisms: APQ handles client-side deduplication, OPcache provides the fastest server-side cache, and the WP object cache serves as fallback.

- **Broader WooCommerce coverage**: Orders, customers, shipping, and settings would be natural candidates for extending the API, with mobile applications as the primary GraphQL clients.

- **Long-term vision** (speculative, but worth considering): gradually deprecate the legacy code in `includes/` and replace it with this new code API, even for internal WooCommerce usage. Any new non-internal code that gets added to WooCommerce would become part of the code API by default. This would ensure that we design the public surface of WooCommerce carefully, since the code API would de facto also be the remote (GraphQL) API. You know, one API to rule them all.
