### Changes proposed in this Pull Request:

`PUT /wc/v3/orders/{id}` (and the equivalent v2 endpoint) silently converted any non-`shop_order` record (specifically a WooCommerce Subscription) into a regular shop order on save.

This PR adds a single upfront type check in `WC_REST_Orders_V2_Controller::update_item()` that rejects the request when the persisted order type doesn't match `shop_order`. The check mirrors the one [`WC_REST_Orders_V1_Controller::update_item()`](../blob/trunk/plugins/woocommerce/includes/rest-api/Controllers/Version1/class-wc-rest-orders-v1-controller.php#L878) already performs.

**Backwards compatibility note**

The only behavior change is that `PUT /orders/{id}` now returns **400 `woocommerce_rest_shop_order_invalid_id` "ID is invalid."** when the target ID is not a `shop_order`. Previously it returned 200 and silently corrupted the record. `GET`/`DELETE /orders/{id}` and `POST /orders` are unchanged.

Closes #63936

### How to test the changes in this Pull Request:

Using the [WooCommerce Testing Instructions Guide](https://developer.woocommerce.com/docs/contribution/testing/writing-high-quality-testing-instructions/), include your detailed testing instructions:

**Prerequisites**

- WordPress install with WooCommerce (this branch) and **WooCommerce Subscriptions** active.
- A REST API key with read/write permissions (WP Admin → WooCommerce → Settings → Advanced → REST API).

**Set up a subscription to target**

1. Create a Simple Subscription product (WP Admin → Products → Add New → set Product data to "Simple subscription").
2. Place an order for it from the front-end, or create one via WP Admin → WooCommerce → Subscriptions → Add Subscription.
3. Note the Subscription ID and confirm:
   ```sh
   wp post get <SUB_ID> --field=post_type
   # Expected: shop_subscription
   ```
   > Take a DB snapshot before running the buggy repro on trunk: `wp db export before-repro.sql`.

**Verify the fix on this branch**

4. Send a destructive PUT against the subscription ID:
   ```sh
   curl -i -X PUT \
     -u 'ck_xxx:cs_xxx' \
     -H 'Content-Type: application/json' \
     -d '{"customer_note":"test via wc/v3/orders against subscription"}' \
     'https://your-site.local/wp-json/wc/v3/orders/<SUB_ID>'
   ```
5. Confirm the response is HTTP `400` with body `{"code":"woocommerce_rest_shop_order_invalid_id","message":"ID is invalid.","data":{"status":400}}`.
6. Confirm the subscription is unchanged:
   ```sh
   wp post get <SUB_ID> --field=post_type
   # Expected: shop_subscription
   wp db query "SELECT id, type FROM $(wp db prefix)wc_orders WHERE id=<SUB_ID>"
   # Expected: shop_subscription (if HPOS is enabled)
   ```
7. Confirm the subscription still appears in WP Admin → WooCommerce → Subscriptions.

**Verify the bug on trunk (optional)**

8. Check out trunk and re-run the same `curl` against a fresh subscription. Expected (buggy) result: HTTP `200` with a regular order JSON, `wp post get` now returns `shop_order`, and the subscription has disappeared from the Subscriptions list and now shows in WP Admin → Orders. Restore from the snapshot before continuing.

**Verify the happy path is intact**

9. Pick any real `shop_order` ID and run a normal update:
   ```sh
   curl -i -X PUT \
     -u 'ck_xxx:cs_xxx' \
     -H 'Content-Type: application/json' \
     -d '{"customer_note":"updated via REST"}' \
     'https://your-site.local/wp-json/wc/v3/orders/<ORDER_ID>'
   ```
   Expected: HTTP `200`, response body shows the updated `customer_note`. Order is unchanged otherwise.
