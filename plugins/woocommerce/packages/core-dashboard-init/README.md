# `@woocommerce/core-dashboard-init`

> **Status: Proof of Concept.** This package is part of an exploratory scaffold for surfacing WooCommerce on the experimental Gutenberg dashboard. APIs, file layouts, and conventions described here will likely move.

A `@wordpress/build` "init module" that runs on dashboard boot and registers WooCommerce-core contributions to the dashboard. Currently registers two Store Activity sources:

- `woocommerce/orders` — recent orders, backed by a WC-side `order` entity that points at `/wc/v3/orders`.
- `woocommerce/reviews` — recent product reviews, backed by a WC-side `review` entity that points at `/wc/v3/products/reviews`. We avoid `root/comment` with `type='review'` because that filter is only a `comment_type` naming convention and doesn't enforce that the parent is a product, so it can leak non-product activity into the widget.

## Why a separate package?

The Store Activity widget exposes a public WordPress filter (`storeActivity.sources`) so any plugin can append sources. The widget itself does **not** ship sources — including WooCommerce core's own (orders, customers, reviews…). The convention is that each contributor registers its sources at boot time via `addFilter`, and the widget reads them at render time via `applyFilters`.

This package is WooCommerce core's contribution to that filter. Other Woo plugins (and third parties) will follow the same shape from their own packages.

## How does it get evaluated?

This is the part that's tentative and a bit hacky today — read carefully.

### What works upstream today

`@wordpress/build` has a formal "Init Modules" pattern (`README.md` of the build tool, sections on `wpPlugin.pages[].init`):

1. A package declares `wpScriptModuleExports` and exports `async function init()`.
2. The package owner adds its name to `wpPlugin.pages[].init` of the **root** `package.json` that owns the page.
3. The build emits a `pages/<slug>/page.php` whose inline script does:
   ```js
   import('@wordpress/boot').then( mod =>
     mod.init( { ..., initModules: ['@my-plugin/my-page-init', ...] } )
   );
   ```
4. `boot.init()` imports each init module and awaits its `init()`.

### Why we can't use it directly

WooCommerce **doesn't own the dashboard page** — `dashboard-wp-admin` is generated by Gutenberg/core. We can't add ourselves to its `wpPlugin.pages[].init` array because that array is baked at build time by Gutenberg, not WooCommerce.

The extension point Gutenberg does expose for other plugins is the `dashboard-wp-admin_boot_dependencies` filter, where we can `'import' => 'static'` arbitrary script modules. **But** for the wp-admin variant of the page template, the generated `pages/<slug>/loader.js` is literally:

```js
// Empty module loader for page dependencies
```

So `boot_dependencies` only end up as `<link rel="modulepreload">` and import-map entries. Nothing imports them, so their top-level code never runs.

### What we do as a workaround

`Loader.php::enqueue_init_module_evaluator()` hooks `admin_enqueue_scripts` and adds an inline dynamic import to the existing `dashboard-wp-admin-prerequisites` script handle:

```php
wp_add_inline_script(
    'dashboard-wp-admin-prerequisites',
    'import("@woocommerce/core-dashboard-init");'
);
```

That import resolves through the import map (set up by the boot deps filter and `modules.php`), and the module evaluates — running its top-level `registerStoreActivitySources()` and registering the filter callback. By the time the Store Activity widget renders and calls `applyFilters( 'storeActivity.sources', [] )`, our source is available.

The module also exports a no-op `async init()` so it's forward-compatible with the formal pattern, in case it ever gets wired through `boot.init()` automatically.

### Known sharp edges

- The handle `dashboard-wp-admin-prerequisites` is an implementation detail of wp-build's `page-wp-admin.php.template`. If upstream renames the handle, the inline script attaches to nothing.
- `wp_add_inline_script` is designed for regular scripts; we rely on the inline body containing `import()` working in non-module context (it does, in every modern browser).
- If several plugins do this workaround, the order of their inline imports is whatever WordPress assembles. Top-level registrations are racy if any source-side hook depends on another source's registration.

### Tentative direction upstream

We're going to **suggest upstream** that `@wordpress/build` either:

- ship a non-empty `pages/<slug>/loader.js` that explicitly `import()`s each `'import' => 'static'` dep, **or**
- expose a `dashboard-wp-admin_init_modules` filter consumed by the page's inline script so plugins can append init modules cleanly without us needing this workaround.

Either fix removes `enqueue_init_module_evaluator` and turns this into a stock init module pattern.

## Why does this package live in `plugins/woocommerce/packages/`?

Because `@wordpress/build` hardcodes its package scan path to `${plugin_root}/packages/*` (`lib/build.mjs:78` of the installed `@wordpress/build`). To be picked up by the build pipeline we have to live here.

That collides with the historical WooCommerce convention where `plugins/woocommerce/packages/` is the home of Composer packages (`action-scheduler`, `blueprint`, `email-editor`, …) and is therefore gitignored. We've solved the conflict pragmatically by adding allowlist exceptions to the gitignore for this specific package — see `plugins/woocommerce/.gitignore` and `plugins/woocommerce/packages/README.md`.

We'll also **suggest upstream** that `@wordpress/build` make the packages directory configurable (something like `wpPlugin.packagesDir`), so the WC-side source can move to a dedicated folder (`js-packages/`, `wp-build-packages/`) and `packages/` returns to its Composer-only role.

## Data layer: `src/data/`

This package registers its own `@wordpress/core-data` entity for orders, in `src/data/`. We can't use stock `getEntityRecords( 'postType', 'shop_order', ... )` because WooCommerce core does **not** register `shop_order` with `show_in_rest: true` (`includes/class-wc-post-types.php:491-530`), so the `/wp/v2/shop_order` endpoint doesn't exist.

Instead we point at the stable, officially-supported REST endpoint `/wc/v3/orders`, which is HPOS-transparent and works the same whether the site uses HPOS or legacy post-meta storage.

```ts
// src/data/constants.ts
export const WC_ORDER_ENTITY: Entity = {
    name: 'order',
    kind: 'woocommerce',            // namespace, like mailpoet uses 'mailpoet'
    baseURL: '/wc/v3/orders',
    key: 'id',
    label: __( 'Order', 'woocommerce' ),
    plural: __( 'Orders', 'woocommerce' ),
    supportsPagination: true,
};
```

`registerWooCommerceOrderEntity()` calls `dispatch( coreStore ).addEntities( [ WC_ORDER_ENTITY ] )`, gated by an idempotency `Set` so multiple boot paths can call it safely. It's invoked from `src/index.ts` **before** `registerStoreActivitySources()` so consumers can `getEntityRecords( 'woocommerce', 'order', ... )` immediately.

Eventually, when more widgets/sources need access to orders (or to other WC entities), this `data/` subdir can graduate to a dedicated `@woocommerce/data` workspace package mirroring the shape of `@mailpoet-next/data`. For now it lives here to keep the PoC cohesive.

## Sources

### Store Activity → Orders

`src/store-activity/orders/use-orders-activity.tsx` is the React hook that the Store Activity widget calls to fetch events. It uses `@wordpress/data` + `@wordpress/core-data` against the entity registered above:

```ts
useSelect( ( select ) => {
    const records = select( coreStore ).getEntityRecords(
        WC_ORDER_ENTITY.kind,   // 'woocommerce'
        WC_ORDER_ENTITY.name,   // 'order'
        { per_page: 10, orderby: 'date', order: 'desc' }
    );
    // ...
}, [] );
```

The hook returns `{ state: 'loading' | 'empty' | 'success', events? }`. Each event has `id`, `icon` (from `@wordpress/icons`), `renderContent` (React render fn that interpolates a link to the order edit screen and the customer name when available), and `datetime` (ISO 8601 for sorting/grouping in the widget).

### Store Activity → Reviews

`src/store-activity/reviews/use-reviews-activity.tsx` is the equivalent hook for product reviews. It reads from the WC-namespaced `woocommerce/review` entity (also registered in `data/`), which points at `/wc/v3/products/reviews` — a WooCommerce-only endpoint that guarantees every returned record is a product review:

```ts
useSelect( ( select ) => {
    const records = select( coreStore ).getEntityRecords(
        WC_PRODUCT_REVIEW_ENTITY.kind,   // 'woocommerce'
        WC_PRODUCT_REVIEW_ENTITY.name,   // 'review'
        {
            per_page: 10,
            orderby: 'date',
            order: 'desc',
            status: 'approved',
        }
    );
    // ...
}, [] );
```

**Why not `root/comment` with `type='review'`?** It looks tempting because `@wordpress/core-data` ships a stock `comment` entity at `/wp/v2/comments`, so no registration is needed. But `type='review'` only filters by `comment_type` — a naming convention — and does not guarantee the parent post is a product. A "Store Activity" widget must surface store activity only, so the safer (and a bit more verbose) path is to consume the WC-namespaced endpoint and register the entity ourselves.

The V3 response includes `product_id` and `product_name` directly, so we don't need to chain `_embed='up'` to inline the parent product. The timeline event renders `<reviewer> on <product>`, with the reviewer name linking to the comment edit screen (`comment.php?action=editcomment&c=…`) and the product name linking to the product edit screen (`post.php?post=…&action=edit`). Both targets are legacy WP-admin pages, so both links use `@wordpress/ui`'s `Link` — same convention as the orders source.
